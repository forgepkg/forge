**Breaking:** secret encryption at rest is required. `[crypto]` names exactly
one root provider, `env` or `file`; `crypto.enabled` is gone, and Forge
refuses to start without a usable root key, naming what to set:
`FORGE_CRYPTO__ROOT__PROVIDER=env` with `FORGE_ROOT_KEY`, or
`FORGE_CRYPTO__ROOT__PROVIDER=file` with `FORGE_CRYPTO__ROOT__ROOT_KEY_PATH`.
The Helm chart uses the `env` provider and refuses to render without
`FORGE_ROOT_KEY` (in `secretEnv`, `existingSecret` or `env`); the kustomize
base sets the provider and the overlays' `forge.env` holds the key.
`GET /admin/crypto/keys` no longer reports `enabled` or
`plaintext_backfill_pending`, and a rotation no longer answers 409 for
encryption being off.

2.0.0 keeps no secret in plaintext: migration 0047 drops what 1.x stored
unencrypted without `[crypto]` (proxy upstream passwords, Nexus import
passwords, realm secrets and email credentials kept in their config, the
registry-token key and the OIDC issuer keys). An install that runs 1.x
without `[crypto]` does this before upgrading:

1. Generate a root key (`openssl rand -base64 32`).
2. Keep it in your secret manager and with your backups.
3. Configure it on 1.x and restart every instance at once, not as a rolling
   update: the 1.x startup encrypts the stored secrets.
4. Upgrade to 2.0.0.

A secret still stored in plaintext when 2.0.0 starts is gone: enter the proxy
passwords, realm secrets and email credentials again; Forge generates a new
registry-token key and new issuer keys. Losing the root key makes the stored
secrets unreadable the same way. Packages and metadata are not affected.
