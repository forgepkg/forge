# Secret encryption at rest (double envelope) — Design & Implementation Plan

**Date:** 2026-05-29
**Slice:** §12.5 of the envisia-forge design (NuGet registry)
**Status:** Draft plan (forward-looking; builds on approved Slice 1)

> Builds on Slice 1 crates (`storage`, `db`, `cache`, `core`, `server`), the
> `db` data-access layer, TOML+`FORGE_*` config loading (§8), the proxy
> `upstream_password` column (stored plaintext-but-redacted in Slice 1, §3/§5),
> and the no-in-memory-only-state / scale-out constraint (§2.1, §13). Does
> **not** restate Slice 1 — see
> `specs/2026-05-29-envisia-forge-nuget-design.md`.

## Goal

Encrypt sensitive values at rest in Postgres using **double envelope
encryption**, starting with the proxy `upstream_password` (today: plaintext in a
redacted column) and generalizing to every future secret (§12.2 OIDC
`client_secret`, §12.3 validated-credential `key_pepper` / upstream bind
password). Plaintext is encrypted by a per-secret **DEK** (Data Encryption Key)
under AEAD; the DEK is wrapped by a **KEK** (Key Encryption Key); the KEK is
wrapped by a **root key** held in a KMS/HSM (or, in lower environments, a root
key from env/file). Two wrapping layers so **KEK rotation re-wraps only DEKs**
(cheap, no ciphertext touched) and **root rotation re-wraps only KEKs** (cheaper
still). Every server instance can encrypt and decrypt because the authoritative
wrapped key material lives in Postgres + KMS — never generated per-instance in
memory.

## Architecture (2–4 sentences)

A new `crypto` crate owns the key hierarchy, the AEAD envelope format, the
`KmsProvider` trait (real KMS + dev file/env root key), and a bounded,
zeroizing cache of *unwrapped* keys. The `db` crate gains a transparent
`EncryptedValue` / `Secret` column type: writes encrypt-on-write under the
current active DEK and bind the ciphertext to the row/column via AEAD associated
data; reads decrypt-on-read. The authoritative state — wrapped KEKs/DEKs (in a
new `encryption_key` table) and the KMS-held root — is shared across all
instances; the unwrapped-key cache is a short-TTL L1 of *derivable* material
(re-unwrappable from Postgres+KMS), so it is a justified, documented exception
to §2.1 rather than authoritative in-memory state. Rotation jobs run per layer
as cluster-coordinated background workers (Postgres advisory locks, the Slice 1
pattern).

## Tech-stack additions

Recommended crates (justified briefly):

- **`aws-sdk-kms`** — real KMS provider. Used only to *wrap/unwrap the root layer*
  (Encrypt/Decrypt of KEKs, or GenerateDataKey if we let KMS mint DEKs in a
  KMS-native variant). Already in the AWS SDK family alongside Slice 1's
  `aws-sdk-s3`, so the credential/region/endpoint plumbing is shared. Optional
  feature flag `kms-aws` so dev builds don't pull it.
- **`aes-gcm`** (RustCrypto) — AES-256-GCM AEAD for the secret/DEK/KEK envelopes.
  Hardware-accelerated on AES-NI hosts, FIPS-friendly, and matches what a KMS
  root typically uses. **Chosen as the default.**
- **`chacha20poly1305`** (RustCrypto, XChaCha20-Poly1305) — alternative AEAD. Its
  **192-bit extended nonce** makes random nonces collision-safe without a
  counter, attractive for the *secret* layer where we want pure-random nonces and
  no per-key counter state. We support both and record the algorithm per row /
  per key (see envelope format); default AES-256-GCM, opt-in XChaCha20.
- **`zeroize`** (+ `zeroize` derive) — scrub unwrapped key bytes and transient
  plaintext from memory on drop. Wrap all in-memory key material in
  `Zeroizing<[u8; 32]>` / a `secrecy`-style newtype.
- **`secrecy`** — `SecretBox`/`SecretString` wrappers that prevent accidental
  `Debug`/`Display`/serialization of secrets and zeroize on drop. Belt-and-braces
  over `zeroize` for the *plaintext secret* type so it never leaks into logs.
- **`rand`** (`rand_core` + `OsRng`) — CSPRNG for nonces and for generating new
  DEK/KEK bytes (already likely present via token generation in Slice 1).
- **`hkdf` + `sha2`** — *optional*, for the file/env dev root provider: derive a
  root wrapping key from a high-entropy root secret + a context label (so the
  same env secret can yield distinct subkeys if ever needed). Likely already
  transitively present.
- **`base64`** — encode ciphertext/nonce/wrapped-key blobs when stored in `text`
  columns and in config; almost certainly already present.

No new async runtime, HTTP, or DB deps — all reuse Slice 1's `tokio`, `reqwest`
(only inside `aws-sdk-kms`), and `sqlx`.

## 1. Scope

### In scope

- A `crypto` crate implementing the **three-layer key hierarchy** (root → KEK →
  DEK), the **versioned AEAD envelope format** (algorithm id + key version +
  nonce + AAD binding + ciphertext+tag), and an `EnvelopeService` that
  encrypts/decrypts secret *values*.
- The **`encryption_key`** table: stores wrapped KEKs and wrapped DEKs with
  version, layer, algorithm, parent reference, and lifecycle state
  (`active` | `retiring` | `revoked`). The root key is **not** stored here (it
  lives in KMS/HSM or env/file); only its identifier/version is referenced.
- A **`KmsProvider` trait** with two impls: `AwsKmsProvider` (real KMS) and
  `FileRootProvider` / `EnvRootProvider` (dev/test/lower-env root key from a
  file or env var). Tests use the file/env impl — **no real KMS needed**.
- A transparent **`EncryptedValue` / `Secret` column type** in `db`:
  encrypt-on-write, decrypt-on-read, AAD bound to `(table, column, row-id)` to
  defeat copy-paste/swap attacks. Applied first to
  `repository.upstream_password`.
- A **bounded, zeroizing in-memory cache of unwrapped keys** (KEKs and DEKs) with
  TTL, plus the §2.1-compliance argument (cache of derivable material, not
  authoritative state).
- **Rotation jobs per layer**, cluster-coordinated:
  - DEK rotation (new active DEK for new writes; old DEKs kept for decrypt until
    a re-encrypt sweep retires them).
  - KEK rotation (mint new KEK, re-wrap all DEKs under it; ciphertext untouched).
  - Root rotation (re-wrap all KEKs under the new root; DEKs/ciphertext
    untouched).
- A **migration** that wraps existing plaintext `upstream_password` values into
  the envelope format (one-time, idempotent, resumable).
- Unit + e2e tests (round-trip, tamper detection, each rotation layer,
  multi-instance decrypt, plaintext-migration, never-return-decrypted-secret).

### Explicitly out of scope

- **KMS/HSM provisioning & IAM policy** — operators provision the KMS key and
  grant forge `Encrypt`/`Decrypt`/`GenerateDataKey`/`DescribeKey`. Forge assumes
  it exists (same posture as §13: shared infra is operated externally).
- **A general secrets-manager UI / per-tenant tenancy model** — we design the
  table for an optional `tenant`/`scope` discriminator on DEKs/KEKs so per-tenant
  keys are a later additive step, but Slice-1 forge is single-tenant; we ship
  **per-secret DEKs** (one DEK per secret value, or a small DEK pool) under one
  KEK chain.
- **Encrypting blobs in S3** — this slice is about *small secret values* in
  Postgres. CAS blob encryption (S3 SSE or client-side) is a separate concern,
  not §12.5.
- **Migrating §12.2/§12.3 secrets** — those slices don't exist yet; this slice
  makes the column type + envelope available so they adopt it. The cross-slice
  note at the end records the intent.
- **Bring-your-own-key / external KMS other than AWS** — the trait makes Azure
  Key Vault / GCP KMS / Vault Transit additive; we ship AWS KMS + file/env only.
- **Quantum-resistant / envelope-over-envelope beyond two wrapping layers** — two
  wrapping layers (KEK + root) is the explicit design; no third.

## 2. Design

### 2.1 Key hierarchy (text diagram)

```
                    ┌───────────────────────────────────────────────┐
                    │            ROOT KEY  (layer: root)             │
                    │  authoritative material in KMS/HSM             │
                    │  (or dev: file/env). NEVER in encryption_key.  │
                    │  identified by root_key_id + root_key_version  │
                    └───────────────┬───────────────────────────────┘
                                    │ Wrap/Unwrap  (KMS Encrypt/Decrypt
                                    │               or AEAD with dev root)
                    ┌───────────────▼───────────────────────────────┐
                    │   KEK  (layer: kek)   — encryption_key rows     │
                    │   stored WRAPPED by the root.                   │
                    │   version N, algorithm, state, root_key_version │
                    │   Few of these; rotated occasionally.           │
                    └───────────────┬───────────────────────────────┘
                                    │ Wrap/Unwrap  (AEAD: KEK encrypts DEK)
                    ┌───────────────▼───────────────────────────────┐
                    │   DEK  (layer: dek)   — encryption_key rows     │
                    │   stored WRAPPED by a KEK (kek_version ref).    │
                    │   version M, algorithm, state, kek_version.     │
                    │   Many possible; one active for new writes.     │
                    └───────────────┬───────────────────────────────┘
                                    │ AEAD encrypt (DEK encrypts plaintext,
                                    │  nonce + AAD bound to row/column)
                    ┌───────────────▼───────────────────────────────┐
                    │  SECRET CIPHERTEXT  — lives in the owning table │
                    │  column (e.g. repository.upstream_password_enc) │
                    │  as a versioned envelope blob. references which  │
                    │  DEK version + nonce + AAD. NEVER plaintext.     │
                    └─────────────────────────────────────────────────┘

Rotation re-wrap surfaces:
  • Root rotation  ⇒ re-wrap KEK rows only        (DEKs + ciphertext untouched)
  • KEK  rotation  ⇒ re-wrap DEK rows only        (ciphertext untouched)
  • DEK  rotation  ⇒ new DEK for new writes; old ciphertext re-encrypted lazily
                     by a sweep, then old DEK marked revoked
```

Wrap relationships are by **version reference**, not by embedding: a DEK row
records `wrapping_kek_version`; a KEK row records `root_key_version`. This is
what makes a single-layer rotation cheap — only the rows at that layer change.

### 2.2 `encryption_key` table schema

```sql
-- migrations/NNNN_encryption_keys.sql
CREATE TABLE encryption_key (
    id                   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    layer                text   NOT NULL CHECK (layer IN ('kek', 'dek')),
    version              int    NOT NULL,        -- monotonic per layer (+scope)
    -- AEAD algorithm of THIS key's own bytes when used to wrap children / data.
    algorithm            text   NOT NULL CHECK (algorithm IN
                              ('aes-256-gcm', 'xchacha20-poly1305')),
    -- The wrapped key material: this key's raw bytes, encrypted by its parent.
    --   kek rows: wrapped by the ROOT (KMS Encrypt output, or dev-root envelope)
    --   dek rows: wrapped by a KEK (envelope produced with that KEK)
    wrapped_key          bytea  NOT NULL,
    -- Parent reference (which wrapping key version produced wrapped_key):
    --   kek rows: root_key_version is set, wrapping_kek_version is NULL
    --   dek rows: wrapping_kek_version is set, root_key_version is NULL
    root_key_id          text   NULL,            -- KMS key id / "file" / "env"
    root_key_version     text   NULL,            -- KMS key version / our label
    wrapping_kek_version int    NULL,            -- FK-ish to a kek row's version
    -- Lifecycle:
    --   active   = used for NEW wraps/encrypts (exactly one active per layer+scope)
    --   retiring = still used to DECRYPT/UNWRAP existing material, not for new
    --   revoked  = no longer used at all (kept for audit; safe to hard-delete
    --              once no child/ciphertext references it)
    state                text   NOT NULL DEFAULT 'active'
                              CHECK (state IN ('active', 'retiring', 'revoked')),
    -- Optional forward-looking multi-tenant / multi-purpose discriminator.
    -- Slice 1 uses a single 'default' scope.
    scope                text   NOT NULL DEFAULT 'default',
    created_at           timestamptz NOT NULL DEFAULT now(),
    rotated_at           timestamptz NULL,        -- when state left 'active'
    UNIQUE (layer, scope, version)
);

-- At most one active key per layer+scope (partial unique index).
CREATE UNIQUE INDEX encryption_key_one_active
    ON encryption_key (layer, scope)
    WHERE state = 'active';

-- Fast "give me the active DEK / KEK for scope" and "all DEKs to re-wrap".
CREATE INDEX encryption_key_layer_scope_state
    ON encryption_key (layer, scope, state);
```

Notes:

- The **root key is never a row here** — only KEKs and DEKs are. KEK rows carry
  `root_key_id` + `root_key_version` so root rotation is "find all KEKs whose
  `root_key_version != current`, unwrap with old root, re-wrap with new, update".
- `wrapping_kek_version` on a DEK row makes KEK rotation "find all DEKs whose
  `wrapping_kek_version != active KEK version`, unwrap with that KEK, re-wrap
  with the active KEK, update".
- `wrapped_key` for a KEK is the KMS `Encrypt` ciphertext (opaque to us) in the
  real-KMS provider, or our own AEAD envelope (root-key-wrapped) in the dev
  provider — the `KmsProvider` abstracts that difference (§2.5).
- We do **not** store any unwrapped key bytes, ever. Recovery from a cold start
  is: read `encryption_key` rows, unwrap KEKs via KMS, unwrap DEKs via KEKs.

### 2.3 AEAD envelope format (versioned)

Every encrypted *secret value* stored in an owning table column is a
self-describing, versioned binary blob. One canonical layout, parsed by `crypto`:

```
byte 0      : format_version  (u8)         -- starts at 1
byte 1      : algorithm_id    (u8)         -- 1 = aes-256-gcm, 2 = xchacha20-poly1305
bytes 2..6  : dek_version     (u32, BE)    -- which DEK row decrypts this
byte 6      : nonce_len       (u8)         -- 12 (GCM) or 24 (XChaCha)
bytes 7..   : nonce           (nonce_len bytes, random per encryption)
then        : ciphertext || tag            -- AEAD output (tag appended by RustCrypto)
```

- **Nonce.** Generated fresh from `OsRng` for **every** encryption. 12 bytes for
  AES-GCM, 24 for XChaCha20. The 24-byte extended nonce is collision-safe under
  pure-random generation at our volumes; for AES-GCM we additionally bound the
  number of encryptions per DEK and rotate DEKs well below the GCM birthday limit
  (§6 nonce-reuse).
- **AAD (associated data) — the swap-attack defense.** Not stored in the blob;
  *recomputed* at encrypt and decrypt time from the row's identity:

  ```
  AAD = b"forge.secret.v1" || table_name || 0x1F || column_name || 0x1F || row_pk_be
  ```

  Binding the ciphertext to `(table, column, row_pk)` means a ciphertext lifted
  from `repository#7.upstream_password` and pasted into `repository#9` (or into a
  future `oidc.client_secret`) **fails decryption** — the AAD won't match. AAD is
  authenticated-but-not-encrypted by AEAD, exactly its purpose.
- **Versioning.** `format_version` lets us evolve the layout; `algorithm_id`
  lets a single table hold rows under different AEADs (e.g. during an
  algorithm migration). `dek_version` is the link into `encryption_key`.
- **Storage column type.** `bytea` for the envelope blob. The Slice-1 plaintext
  `upstream_password text` is replaced by `upstream_password_enc bytea` (new
  column; migration copies+encrypts then drops the old — see §2.7).

### 2.4 The `db` transparent column type (`Secret` / `EncryptedValue`)

Goal: callers in `core` read/write secrets as plaintext through `db`; encryption
is invisible. The plaintext type is a zeroizing secret wrapper so it can't leak.

```rust
// crates/crypto/src/secret.rs — illustrative
use secrecy::SecretString;

/// Plaintext secret as seen by callers. Never Debug/Serialize the inner value.
pub type PlaintextSecret = SecretString;   // zeroizes on drop, redacts on Debug

// crates/crypto/src/envelope.rs — illustrative
pub struct AeadBinding<'a> {
    pub table: &'a str,
    pub column: &'a str,
    pub row_pk: i64,
}

pub trait EnvelopeService: Send + Sync {
    /// Encrypt plaintext under the current ACTIVE DEK, binding AAD to the row.
    fn seal(&self, pt: &PlaintextSecret, b: AeadBinding<'_>)
        -> Result<Vec<u8>, CryptoError>;   // returns the envelope blob
    /// Decrypt an envelope blob, verifying AAD == this row's binding.
    fn open(&self, blob: &[u8], b: AeadBinding<'_>)
        -> Result<PlaintextSecret, CryptoError>;
}
```

In `db`, the column read/write goes through `EnvelopeService`. Because the AAD
needs the **row primary key**, encryption can't happen blindly in a sqlx type
codec that doesn't know the row id; instead we encrypt/decrypt in the
**data-access methods** that already know the entity. Concretely:

```rust
// crates/db/src/repository_dal.rs — illustrative
impl RepositoryDal {
    pub async fn set_upstream_password(
        &self, repo_id: i64, secret: Option<&PlaintextSecret>,
    ) -> Result<(), DbError> {
        let blob = match secret {
            Some(pt) => Some(self.envelope.seal(pt, AeadBinding {
                table: "repository", column: "upstream_password_enc", row_pk: repo_id,
            })?),
            None => None,
        };
        sqlx::query!("UPDATE repository SET upstream_password_enc = $2 WHERE id = $1",
                     repo_id, blob).execute(&self.pool).await?;
        Ok(())
    }

    pub async fn get_upstream_password(
        &self, repo_id: i64,
    ) -> Result<Option<PlaintextSecret>, DbError> {
        let row = sqlx::query!("SELECT upstream_password_enc FROM repository WHERE id=$1",
                               repo_id).fetch_one(&self.pool).await?;
        match row.upstream_password_enc {
            Some(blob) => Ok(Some(self.envelope.open(&blob, AeadBinding {
                table: "repository", column: "upstream_password_enc", row_pk: repo_id,
            })?)),
            None => Ok(None),
        }
    }
}
```

For ergonomics we provide a thin `EncryptedColumn` helper in `db` so each
secret-bearing field is one call, and the AAD `(table, column)` constants live
next to the entity to keep them honest. **Transparency** is "callers see
`PlaintextSecret`, never the blob"; we deliberately keep AAD explicit rather than
hiding it in a magic sqlx codec, because the row-pk binding is the whole security
property and must not be silently wrong.

> **Redaction stays.** The Slice-1 rule that `upstream_password` is redacted from
> every API response (§5) is unchanged: admin reads return `"***"` / omit the
> field; the *only* place plaintext is materialized is the proxy upstream-fetch
> path in `core`, which needs it to build the outbound Basic header (§7). This is
> tested (§5 "never returned by admin APIs").

### 2.5 `KmsProvider` trait + dev impl

The root layer is abstracted so tests don't need a real KMS. The trait operates
on **KEK material only** (root wraps KEKs; nothing else touches root).

```rust
// crates/crypto/src/kms.rs — illustrative
#[async_trait::async_trait]
pub trait KmsProvider: Send + Sync {
    /// Identifier of the current root key (KMS key id, or "file"/"env").
    fn root_key_id(&self) -> &str;
    /// Current root key version/label (KMS rotates; dev = our label).
    async fn current_root_version(&self) -> Result<String, CryptoError>;
    /// Wrap (encrypt) raw KEK bytes under the root. Returns opaque wrapped blob.
    async fn wrap_kek(&self, kek_plaintext: &[u8]) -> Result<Vec<u8>, CryptoError>;
    /// Unwrap (decrypt) a wrapped KEK produced under root_version.
    async fn unwrap_kek(&self, wrapped: &[u8], root_version: &str)
        -> Result<Zeroizing<Vec<u8>>, CryptoError>;
}
```

- **`AwsKmsProvider`** (feature `kms-aws`): `wrap_kek` = `kms:Encrypt`,
  `unwrap_kek` = `kms:Decrypt` (KMS ciphertext is self-describing, so
  `root_version` is advisory/audit). `current_root_version` via `DescribeKey`.
  The root key never leaves KMS — exactly the HSM-backed property we want.
- **`FileRootProvider` / `EnvRootProvider`** (dev/test/lower-env): the root key
  is 32 bytes of high-entropy material loaded from a file path or an env var
  (base64). `wrap_kek`/`unwrap_kek` are local AES-256-GCM (or XChaCha20) with the
  root key, a random nonce, and AAD `b"forge.root.wrap"`. `current_root_version`
  is a configured label (e.g. a sha256 prefix of the root bytes) so root rotation
  is "swap the file/env value, bump the label". **Tests use this** — fast,
  hermetic, no network.
- **Selection** is config-driven (`crypto.root.provider = "aws-kms" | "file" |
  "env"`), validated at startup. Refusing to boot if the configured provider
  can't produce a root version surfaces misconfig early.

All instances use the **same** provider config, so all instances reach the same
root → can unwrap the same KEKs → can decrypt every secret. This is the core
scale-out property: **key material is reachable by all instances from KMS/shared
config, never generated per-instance.**

### 2.6 Key caching of unwrapped keys + zeroization + §2.1 compliance

Unwrapping a KEK (KMS round-trip) or a DEK (AEAD under a KEK) on every secret
read would be slow and would hammer KMS. So `crypto` keeps a **bounded,
TTL'd, zeroizing L1 cache of unwrapped keys**:

- **What is cached:** unwrapped DEK bytes (keyed by `dek_version`) and unwrapped
  KEK bytes (keyed by `kek_version`). Wrapped in `Zeroizing<[u8;32]>`; the cache
  entry zeroizes the bytes on eviction/expiry/drop.
- **Implementation:** `moka` (the Slice-1 L1 cache crate) with a small max
  capacity and a short TTL (e.g. 300s), `try_get_with` singleflight so a burst of
  reads unwraps once. **No Redis / no L2** for unwrapped keys — we deliberately
  do **not** put *unwrapped* key bytes in Redis (that would be plaintext key
  material in a shared store). The L2-shareable thing is the *wrapped* material,
  which already lives authoritatively in Postgres.
- **Eviction on rotation:** when a key's state moves to `revoked`, the rotation
  worker fires the Slice-1 cache invalidation backplane to drop that key from
  every instance's L1 (so a revoked key stops being used promptly). `retiring`
  keys stay cached (still needed to decrypt old ciphertext).

**§2.1 compliance (the nuance, documented).** §2.1 forbids *authoritative*
state living in process memory only. The unwrapped-key cache does **not**
violate this:

- The **authoritative** key material is the **wrapped** KEK/DEK rows in Postgres
  + the **root** in KMS/shared config. A cold instance with an empty cache
  reconstructs every unwrapped key by reading Postgres and calling the KMS/file
  root provider — it never needs another instance's memory.
- The cache holds only **derivable** material (re-unwrappable at will), exactly
  like Slice 1's proxy-metadata / registration L1 caches are derivable from
  Postgres/S3. The only twist is that unwrapped *plaintext key bytes* may live
  briefly in RAM for performance — but that's an inherent property of "every
  instance can decrypt" (you can't decrypt without the key in memory for the
  duration of the operation), and it is bounded by TTL + zeroized on drop. We
  record this as the one place where short-lived plaintext key material is
  permitted, contrasted explicitly with the no-in-memory-*authoritative*-state
  rule.

### 2.7 Rotation per layer

All three rotations run as **cluster-coordinated background workers** in
`server` (one tokio task per layer, each grabbing a **Postgres advisory lock** so
only one instance performs a given rotation — the Slice-1 coordination pattern).
Each is **idempotent and resumable** (re-running after a crash continues).

**DEK rotation (cheapest write-path change, costliest data sweep):**
1. Generate a new 32-byte DEK (`OsRng`), wrap it under the **active KEK**, insert
   an `encryption_key` row `layer='dek', state='active'`; flip the previous
   active DEK to `retiring` (single transaction; the partial unique index
   guarantees exactly one active). New writes now use the new DEK.
2. **Lazy re-encrypt sweep** (background, batched): for each table+column that
   stores secrets, find rows whose envelope `dek_version` is a `retiring` DEK,
   `open` with that DEK and `seal` with the active DEK (AAD recomputed — same
   row, so unchanged), `UPDATE` the row. Batch with `LIMIT`/keyset pagination;
   each batch its own transaction. When no ciphertext references a `retiring` DEK
   anymore, mark it `revoked`.
3. Rotation cadence and trigger: scheduled (config `crypto.dek.max_age_days`) and
   on-demand via an admin endpoint. Also auto-rotated if a DEK approaches its
   GCM encryption-count budget (§6).

**KEK rotation (re-wraps DEKs only — ciphertext untouched):**
1. Generate a new KEK (`OsRng`), wrap it under the **current root** (`KmsProvider
   .wrap_kek`), insert `layer='kek', state='active'`; flip old KEK to `retiring`.
2. **Re-wrap sweep:** for each DEK row, unwrap with its current
   `wrapping_kek_version` KEK, re-wrap under the new active KEK, update
   `wrapped_key` + `wrapping_kek_version`. Secret ciphertext is **never read or
   written** — only `encryption_key.wrapped_key` of DEK rows changes.
3. When no DEK references the old KEK, mark it `revoked` and invalidate the
   unwrapped-KEK cache entry.

**Root rotation (re-wraps KEKs only — DEKs + ciphertext untouched):**
1. For KMS: the new root version is created in KMS (operator action or KMS
   auto-rotation); forge learns it via `current_root_version`. For dev: operator
   swaps the file/env root value and bumps the label.
2. **Re-wrap sweep:** for each KEK row whose `root_key_version != current`,
   `unwrap_kek(old)` then `wrap_kek(new)`, update `wrapped_key` +
   `root_key_version`. Only `encryption_key` KEK rows change.
3. KMS-native note: AWS KMS automatic key rotation keeps the *same* key id and
   transparently uses the new backing key for new `Encrypt`s while still
   `Decrypt`ing old ciphertext — so with `kms:Encrypt`/`Decrypt` wrapping, root
   rotation can be a **no-op re-wrap** (KMS handles it). We still expose the
   explicit re-wrap path for the file/env provider and for forced rotation.

Rotation atomicity: each key-row state change is one transaction; each data/
re-wrap batch is one transaction; the active-key flip uses the partial unique
index so there is never zero or two active keys. A crash mid-sweep leaves a
consistent mix (some rows on new key, some on old) that the next run finishes —
both old and new keys are valid (`active`/`retiring`) during the window.

### 2.8 Plaintext → encrypted migration

Slice 1 stores `repository.upstream_password text` in plaintext (redacted in
APIs). Migration steps:

1. **Schema migration** `migrations/NNNN_encrypt_upstream_password.sql`: add
   `upstream_password_enc bytea NULL`. Keep the old `upstream_password text`
   column for now (don't drop in the same migration — see step 4).
2. **Bootstrap keys:** on first run after this slice ships, `server` startup
   ensures an active KEK and active DEK exist (create-if-absent under the
   configured root provider). This is idempotent and advisory-locked so two
   instances starting together create exactly one.
3. **Data migration job** (a one-shot, resumable background task, advisory-locked
   so it runs once cluster-wide): `SELECT id, upstream_password FROM repository
   WHERE upstream_password IS NOT NULL AND upstream_password_enc IS NULL` in
   batches; for each, `seal` under the active DEK with AAD bound to
   `(repository, upstream_password_enc, id)`; `UPDATE` the `_enc` column. Idempotent
   (the `IS NULL` guard makes re-runs skip done rows).
4. **Cutover + cleanup** (separate, later migration once the job has fully run and
   been verified — gated so we never drop plaintext before ciphertext exists):
   `ALTER TABLE repository DROP COLUMN upstream_password;` and rename
   `upstream_password_enc` → `upstream_password` (or keep the `_enc` name and
   update the data-access; we keep `_enc` to make "this column is encrypted"
   obvious in the schema). The proxy upstream-fetch code in `core` switches from
   reading the plaintext column to `RepositoryDal::get_upstream_password`.

This two-migration approach (add+backfill, then drop) is the standard safe
column-rewrite pattern and lets us verify ciphertext before destroying
plaintext.

## 5. Security & failure modes

- **Nonce reuse.** Catastrophic for AES-GCM (key+nonce reuse breaks
  confidentiality and forgeable). Mitigations: nonces from `OsRng` per
  encryption; **per-DEK encryption budget** (`dek_max_encryptions`, well under
  GCM's ~2³² random-96-bit-nonce birthday bound) that forces DEK rotation before
  the collision probability is non-negligible; XChaCha20-Poly1305 option whose
  192-bit nonce removes the practical concern entirely (recommended for
  very-high-write secret tables, though secrets here are low-write). We never use
  a deterministic/counter nonce shared across instances (multiple writers ⇒ pure
  random is safer than a shared counter we'd have to coordinate).
- **AAD binding.** Ciphertext is bound to `(table, column, row_pk)`; a blob moved
  to another row/column/table fails to decrypt — defeats copy-paste/swap and
  cross-secret confusion. Tested at both `crypto` and `db` layers. *Caveat:* AAD
  binds to the **primary key**, so if a row is hard-deleted and the PK reused
  (identity PKs don't reuse, so this is moot for us — noted) the binding would
  shift; identity PKs make this safe.
- **Key compromise blast radius.**
  - *DEK leak:* exposes only secrets sealed under that DEK; rotate DEK + revoke.
  - *KEK leak:* exposes DEKs it wraps (hence the secrets); rotate KEK (re-wrap
    DEKs) + revoke; consider a DEK rotation too if the KEK leak implies the DEKs
    were exposed.
  - *Root/KMS-key compromise:* worst case — can unwrap all KEKs. Mitigated by
    keeping root in KMS/HSM (never extractable in the AWS impl), KMS audit logs
    (CloudTrail), and least-privilege IAM (forge gets `Encrypt`/`Decrypt` on one
    key, not key export). Two layers mean a root rotation re-protects everything
    by re-wrapping KEKs without touching the bulk ciphertext.
- **Rotation atomicity.** Per-row state flips and per-batch re-wrap/re-encrypt are
  single transactions; the **partial unique index** guarantees exactly one
  `active` key per layer; `retiring` keys remain usable for decrypt during the
  window, so a crash mid-rotation leaves a consistent, fully-decryptable mix that
  the next (advisory-locked) run completes. No global stop-the-world.
- **KMS outage behavior.** If the root provider is unreachable: (a) **reads** of
  secrets whose DEK is already in the unwrapped-key cache still work (bounded by
  TTL); (b) reads needing a cold unwrap **fail closed** (error, not a default to
  plaintext/empty) — the proxy upstream-fetch then can't authenticate and the
  fetch fails, which is the safe outcome; (c) **writes** of new secrets that need
  a new KEK fail; existing-KEK writes (new DEK already cached/unwrappable) can
  proceed. We log + metric KMS errors distinctly. We do **not** cache *wrapped→
  unwrapped* across the outage beyond the normal TTL (no special outage cache),
  to bound the trust window. Operators should provision KMS HA (out of scope per
  §13).
- **Memory disclosure / zeroization limits.** Unwrapped keys and transient
  plaintext live in RAM during crypto operations — unavoidable for "every
  instance can decrypt". We minimize the window (bounded TTL, zeroize on
  drop/evict via `zeroize`/`secrecy`). **Documented limits:** `zeroize` cannot
  defeat (a) values copied by the allocator/`realloc` before we held them, (b)
  swap-to-disk (operators should disable swap or use encrypted swap / mlock —
  noted as ops guidance), (c) core dumps (disable for the process), (d) a
  compromised process with debugger access. Zeroization reduces, not eliminates,
  cold-boot / memory-scrape exposure. We never log key bytes or plaintext
  secrets (the `secrecy`/redaction discipline + the §5 redaction rule).
- **Never-return-decrypted-secret.** Admin APIs redact secret values and the
  `GET /admin/crypto/keys` endpoint returns metadata only. The single sanctioned
  decrypt site is the proxy upstream-fetch in `core`. Enforced by tests (§4 #9)
  and by the `PlaintextSecret` type refusing `Serialize`/`Debug`.
- **At-rest vs in-transit.** This slice covers at-rest. The user's plaintext
  upstream password still travels to the upstream over the proxy fetch's Basic
  header (Slice-1 behavior, requires HTTPS upstream) — unchanged here.

## 6. Open questions / risks

1. **Slice-1 proxy fetch read site.** Plan assumes the proxy upstream-fetch reads
   `upstream_password` in one identifiable `core` location that can switch to
   `RepositoryDal::get_upstream_password`. If it's read inline in several places,
   Phase 3 is slightly larger. *Assumption flagged.*
2. **Slice-1 cache-crate invalidation API.** Phase 4 assumes the `cache` crate's
   invalidation backplane (§2.1) can carry a "drop unwrapped key version K"
   message. If its API is hard-coded to proxy/registration namespaces, a small
   generalization is needed (same assumption §12.3 flagged). *Flagged.*
3. **Per-secret vs per-tenant DEK granularity.** We ship a single active DEK
   shared by all secrets (with rotation), not one DEK per secret value. True
   per-secret DEKs increase isolation but multiply key rows and rotation cost.
   The `scope` column + `dek_version` design makes per-tenant or per-purpose DEKs
   an additive change; revisit if §12.6 multi-tenancy lands. *Decision: shared
   active DEK for Slice §12.5; documented.*
4. **KMS-native DEK minting (`GenerateDataKey`).** An alternative is to let AWS
   KMS mint DEKs directly (returns plaintext+wrapped DEK), skipping our KEK layer
   for the AWS provider. We **keep the explicit KEK layer** so the hierarchy is
   uniform across providers (file/env has no `GenerateDataKey`) and so KEK
   rotation is cheap. Risk: slightly more code than a pure KMS-DEK design.
   *Decision recorded.*
5. **Root rotation for the file/env provider** requires an operator to keep the
   *old* root reachable until the KEK re-wrap sweep completes (we need the old
   root to unwrap, the new to re-wrap). Plan: config accepts a *previous* root
   (`root_key_env_previous`) during a rotation window; document the procedure.
   *Risk: operator error; mitigated by docs + a startup check that all KEKs'
   `root_key_version` are unwrappable before declaring ready.*
6. **GCM encryption budget enforcement.** `dek_max_encryptions` must be tracked
   per DEK to trigger rotation. We can count via a cheap `encryption_key` counter
   column bumped opportunistically, or estimate from row counts. Exact tracking
   adds a write on the secret hot path; for low-write secret tables an estimate
   suffices. *Open: exact-count column vs estimate; default to a generous budget
   + periodic check.*
7. **Re-key during high churn.** If a secret is updated while a DEK sweep is
   re-encrypting it, the last writer wins and both old/new DEK decrypt correctly
   during the window; we rely on row-level `UPDATE` atomicity. Believed safe;
   covered by the crash-resume test (§4 #10) but worth an adversarial review.
8. **Compliance posture (FIPS).** If a deployment needs FIPS-validated crypto,
   RustCrypto's pure-Rust AES-GCM may not qualify; an alternative is routing all
   AEAD through KMS or a FIPS module. Out of scope to implement; flagged so the
   `algorithm`/provider seam is kept pluggable.
