# Fine-grained RBAC + nested groups — Design & Implementation Plan

**Date:** 2026-05-29
**Slice:** §12.4 of the `envisia-forge` design (depends on the approved Slice 1 spec,
`2026-05-29-envisia-forge-nuget-design.md`)
**Status:** Draft — forward-looking plan

## Goal

Replace slice 1's coarse authorization ("any authenticated `User` may read/write
any repo; `Anonymous` may read iff `repository.anonymous_read`; admin API needs
`is_admin`") with a **fine-grained RBAC model**: named **roles** that grant
**privileges** (`read` / `write` / `delete` / `admin`) scoped to specific
repositories, optionally narrowed by **content selectors** (package-name / version
patterns). Roles are assigned to users (and to a built-in **anonymous** role and a
built-in **admin** role). Tokens may optionally **scope down** their owner's
privileges. The same model also enables **nested group repositories** (groups whose
members are themselves groups) with **cycle detection** at config time and at
resolve time. Every privilege decision stays correct across multiple stateless
instances and stays fast on the hot read/download path via the slice-1 `cache`
crate with cross-node invalidation.

## Architecture (overview)

RBAC lives in `core` as an `authz` module that **owns the `can_read` / `can_write`
/ `can_admin` seam** slice 1 already calls — we replace the coarse bodies of those
functions, not their signatures or call sites. Authoritative privilege data lives
in new Postgres tables (`role`, `privilege`, `role_privilege`, `user_role`,
`repository_privilege`, `content_selector`); the resolved **effective-permission
set** for a principal is computed by a single SQL query and cached through the
slice-1 `cache` crate (L1 moka + optional Redis L2), keyed by principal, with
**explicit invalidation broadcast on the backplane** whenever a role/privilege/
assignment changes. Nested-group membership reuses the slice-1 `group_member`
table (lifting its "member must be hosted/proxy" check) plus a cycle guard, and the
identity-aware group-resolution filter is rewired from `anonymous_read` to
`can_read(principal, member)` so member visibility now honors privileges.

## Tech-stack additions (recommended Rust crates)

- **`globset`** (or `glob`) — for content-selector pattern matching against
  lowercased package names (e.g. `Company.*`, `Internal.Tools.?`). `globset`
  compiles a `GlobSet` once per selector and matches in constant-ish time; it is
  the standard, well-audited choice and avoids hand-rolled glob parsing. Patterns
  are compiled at selector load and cached alongside the effective-permission set.
- **No regex by default.** Content selectors use **glob** semantics (Nexus uses a
  CSEL/JEXL DSL, JFrog uses Ant globs — we mirror the simpler Ant/glob subset).
  Optional future regex is an Open Question, not in this slice.
- Everything else (`sqlx`, `moka`, optional `redis`, `tokio`, `axum`) is reused
  from slice 1. No new workspace member crate.

## 2. Scope

### In scope
- `role`, `privilege` (seeded reference rows), `role_privilege`, `user_role`,
  `repository_privilege`, `content_selector`, `repository_privilege_selector`
  tables.
- Built-in seeded roles: **`admin`** (all actions, all repos), **`anonymous`**
  (assigned to every `Anonymous` principal), and a convenience **`authenticated`**
  default (see migration §3 / Phase 5) used only to preserve slice-1 behavior.
- Action set: **`read`**, **`write`** (push/relist), **`delete`** (hard delete /
  unlist beyond owner), **`admin`** (repo config + privilege management). A small,
  faithful subset of Nexus/JFrog (see §3 "Parity survey").
- Per-repository privilege grants, with an **`ANY`/all-repositories** wildcard grant
  (mirrors Nexus `*` repository and JFrog `ANY`).
- Optional **content selectors**: include/exclude glob patterns on package name
  (and optionally version), attached to a `repository_privilege` grant; **additive
  / grant-only** semantics (a selector can only *widen* nothing — it scopes a single
  grant; another grant without a selector still grants broadly). Matches Nexus's
  "privileges grant, never restrict" rule.
- Migration of the slice-1 `is_admin` flag → membership in the built-in `admin`
  role (column kept, dual-read during transition, then `admin` role authoritative).
- Mapping `Anonymous` principal → the built-in `anonymous` role; `anonymous_read`
  on `repository` is migrated into `anonymous`-role `read` grants so behavior is
  preserved.
- **Optional per-token privilege scoping**: a token may carry a privilege scope
  (subset of its owner's grants) so a CI token can be locked to `read` on one repo.
- Replacement of `can_read` / `can_write` / `can_admin` bodies with the
  effective-permission evaluator; **same signatures, same call sites**.
- Effective-permission **caching** (L1+L2 via `cache`) keyed by principal, with
  **cross-instance invalidation** on any role/privilege/assignment/selector/token
  change.
- **Nested group membership** + **cycle detection** at config time (admin API
  rejects a member edge that would create a cycle) and at resolve time
  (visited-set guard + depth bound, fail-closed).
- Admin REST endpoints to CRUD roles, privileges-on-roles, user-role assignments,
  repository-privilege grants, content selectors, and token scopes.
- Unit + e2e tests including a principal × repo × action matrix, token scoping,
  anonymous role, nested-group visibility honoring privileges, cycle rejection
  (config + runtime), and cross-instance cache invalidation on privilege change.

### Explicitly out of scope
- **Retention/GC content selectors (§12.1).** §12.1 already adds a
  `retention_policy` and may grow a notion of "which packages a policy targets."
  This slice's `content_selector` is an **authorization** filter; §12.1's targeting
  is a **lifecycle** filter. They are deliberately **separate concepts**; see
  Open Questions for a possible later unification of the selector *expression*
  language only. We do not couple them here.
- **Identity sources (§12.2 OIDC, §12.3 credential-forwarding).** This slice maps
  *existing* `app_user` rows to roles. How a user is *authenticated* or
  *provisioned* (OIDC claims, group claims, upstream basic) is those slices' job.
  We define a clean seam — "given an authenticated `user_id`, what roles does it
  hold?" — that §12.2/§12.3 can later populate (e.g. claim-/group-driven role
  mapping). We do **not** build claim→role mapping here.
- The admin **UI** (§12.6). This slice ships the REST API only.
- Secret encryption (§12.5), retention (§12.1), additional formats (§12.7).
- Group-/team-of-users RBAC indirection (Nexus "roles containing roles"). We
  support roles → privileges and users → roles; **role nesting (a role that
  includes another role) is deferred** (see Open Questions) — only *repository
  group nesting* is in scope. This keeps the privilege evaluator a single flat
  join.

## 3. Design

### Parity survey (Nexus + JFrog → the subset we reflect)

| Concept | Nexus Repo 3 | JFrog Artifactory | envisia-forge §12.4 |
|---|---|---|---|
| Grouping of permissions | **Role** (set of privileges; roles can nest) | implicit via **permission target** | **`role`** (flat: role→privileges; no role nesting this slice) |
| Atomic permission | **Privilege** typed (`repository-view`, `repository-admin`, `repository-content-selector`, application, script, wildcard) | actions on a permission target | **`repository_privilege`** = (role, repo|ANY, action) grant |
| Actions | `browse`, `read`, `edit`, `add`, `delete`, `*` | `read`, `deploy/write`, `delete`, `annotate`, `manage` | **`read`, `write`, `delete`, `admin`** (4; `browse`≈`read`, `add`+`edit`≈`write`, `manage`≈`admin`) |
| Repo wildcard | `*` repository | `ANY` / `ANY LOCAL` / `ANY REMOTE` | **`ANY`** (null `repository_id` ⇒ all repos) |
| Content scoping | **Content selector** (CSEL/JEXL on path/format) | **include/exclude patterns** (Ant globs) | **`content_selector`** (glob include/exclude on package name) |
| Combination rule | **Additive, grant-only** ("privileges grant, do not restrict") | union of permission targets | **Additive, grant-only** — a deny is the *absence* of a grant, never an explicit deny edge |
| Anonymous | `nx-anonymous` user + role | `anonymous` user | built-in **`anonymous`** role auto-applied to `Anonymous` principals |
| Admin | `nx-admin` role = `nexus:*` | `admin`/`manage` | built-in **`admin`** role = all actions on `ANY` repo + privilege management |

Key adopted principle (from Nexus): **privileges are purely additive and
grant-only.** There are no explicit deny rows; "no access" is the default and the
fail-closed state. A content selector therefore *scopes a single grant down* — it
does not subtract from other grants. This keeps evaluation a monotonic OR over
grants and avoids the well-known deny-precedence footguns.

### Data model

`bigint` generated identity PKs; timestamps `timestamptz`; consistent with slice 1.

```sql
-- A named, assignable role.
CREATE TABLE role (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name        TEXT NOT NULL UNIQUE,          -- url-safe slug, e.g. 'admin','anonymous','ci-readers'
    description TEXT NOT NULL DEFAULT '',
    builtin     BOOLEAN NOT NULL DEFAULT FALSE, -- builtin roles cannot be deleted; grants restricted
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Reference table of action verbs. Seeded, immutable. Acts as an FK target /
-- enum-in-a-table so the action set is queryable and extensible.
CREATE TABLE privilege (
    action TEXT PRIMARY KEY                    -- 'read' | 'write' | 'delete' | 'admin'
);
INSERT INTO privilege(action) VALUES ('read'),('write'),('delete'),('admin');

-- Which actions a role may exercise, in the abstract (the repo scoping is on the
-- grant). Kept separate from repository_privilege so a role's action vocabulary
-- and its repo grants are independent and queryable. OPTIONAL — see note below.
-- We instead fold action onto the grant row (repository_privilege.action) to keep
-- the evaluator a single join; role_privilege is therefore NOT created.
-- (Documented decision: action lives on the grant, not on a role_privilege table.)

-- A grant: "this role gets <action> on <repo or ANY>, optionally scoped by a
-- content selector." This is the core of the model.
CREATE TABLE repository_privilege (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    role_id       BIGINT NOT NULL REFERENCES role(id) ON DELETE CASCADE,
    repository_id BIGINT NULL REFERENCES repository(id) ON DELETE CASCADE, -- NULL = ANY repo
    action        TEXT NOT NULL REFERENCES privilege(action),
    selector_id   BIGINT NULL REFERENCES content_selector(id) ON DELETE CASCADE,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- A given (role, repo|ANY, action, selector) edge is unique. NULLs compared via
-- COALESCE-based unique index so (role, NULL repo, read, NULL sel) is single.
CREATE UNIQUE INDEX repository_privilege_uq
    ON repository_privilege (role_id, COALESCE(repository_id, 0), action, COALESCE(selector_id, 0));
CREATE INDEX repository_privilege_role_idx ON repository_privilege (role_id);
CREATE INDEX repository_privilege_repo_idx ON repository_privilege (repository_id);

-- Assignment of roles to users.
CREATE TABLE user_role (
    user_id BIGINT NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
    role_id BIGINT NOT NULL REFERENCES role(id) ON DELETE CASCADE,
    PRIMARY KEY (user_id, role_id)
);
CREATE INDEX user_role_role_idx ON user_role (role_id);

-- A reusable named content selector: include/exclude globs on package name.
CREATE TABLE content_selector (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name         TEXT NOT NULL UNIQUE,
    description  TEXT NOT NULL DEFAULT '',
    -- include/exclude as jsonb arrays of glob strings matched against lowercased
    -- NuGet package name. Empty include ⇒ match-all (then exclude subtracts).
    includes     JSONB NOT NULL DEFAULT '["*"]',
    excludes     JSONB NOT NULL DEFAULT '[]',
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**Per-token scoping** extends the slice-1 `token` table additively:

```sql
-- A token MAY carry a scope that intersects (never widens) its owner's grants.
-- NULL scope ⇒ token inherits the full set of its owner's effective privileges.
ALTER TABLE token ADD COLUMN scope JSONB NULL;
-- scope shape (validated in code): { "actions": ["read"], "repositories": ["feed-a","feed-b"] }
-- 'repositories' omitted ⇒ all repos the owner can touch; 'actions' omitted ⇒ all
-- of the owner's actions. The effective set is owner_set ∩ scope (intersection).
```

Anonymous needs no extra table: a config-seeded `anonymous` role plus the rule
"every `Anonymous` principal is treated as holding exactly the `anonymous` role's
grants." The migration converts `repository.anonymous_read = true` into a
`(anonymous role, that repo, read)` grant, so existing behavior is preserved
without keeping `anonymous_read` on the hot path (column retained for one release as
a fallback / audit, then dropped in a follow-up — see Phase 5).

`group_member` is **reused unchanged structurally**; the slice-1 config-time check
"`member_id` must be hosted/proxy" is *replaced* by "may be any repo, but the edge
must not create a cycle and a configurable max depth must not be exceeded"
(Phase 6).

### The permission model

A principal's **effective grant set** is the union (additive) of grants from all
roles it holds:

- **User principal** holds: roles in `user_role` for its `user_id`. If the user is
  in the built-in `admin` role → short-circuit allow-all.
- **Anonymous principal** holds: exactly the built-in `anonymous` role's grants.
- **Token-authenticated user**: owner's effective set **intersected** with the
  token's `scope` (if any). A token can never grant more than its owner has — it
  only narrows. (Mirrors GitHub fine-grained PATs / least privilege.)

Each grant is `(action, repo_match, selector?)` where `repo_match` is a specific
`repository_id` or `ANY`. A request for `action A` on `repo R` for package `P` is
**allowed iff** there exists a held grant where:

```
grant.action == A
AND (grant.repository_id IS NULL OR grant.repository_id == R.id)
AND (grant.selector IS NULL OR selector_matches(grant.selector, P))   -- P only known on package-scoped ops
```

For repo-level operations with **no package context** (e.g. `GET
/v3/{repo}/index.json`, service-index, search enumeration), a grant **with a content
selector still counts as "may read this repo"** — selectors filter *which packages*
are visible within the response, not whether the repo is reachable. So evaluation
has two flavors:

- `can_read(principal, repo)` / `can_write` / `can_admin` → **repo-level**: "does
  any held grant for this action cover this repo?" (selector ignored for the
  gate; a selector-scoped read grant still passes the repo gate).
- `visible_packages(principal, repo)` → returns the **selector predicate** to apply
  when listing/serving packages (flat container, registration, search, direct
  download): a package is visible iff at least one held `read` grant covering this
  repo either has no selector or matches the package. Direct download of a specific
  `id/version` re-checks this predicate and 404s (not 403 — avoid existence leak)
  when no grant matches.

This keeps the hot **repo gate** a tiny set-membership test while still supporting
package-level scoping where it matters.

#### `is_admin` migration to a role

The built-in `admin` role is seeded with a single sentinel grant
`(admin role, repository_id = NULL/ANY, action = 'admin')` *and* the evaluator
treats membership in the `admin` role as **allow-all** (read/write/delete/admin on
every repo, plus access to privilege-management endpoints). The migration inserts a
`user_role(user_id, admin_role_id)` row for **every `app_user` with
`is_admin = true`**. During a transition window the evaluator's admin check is
`user_in_admin_role OR app_user.is_admin` (dual-read, fail-open *toward existing
admins* only — never toward non-admins). A later migration drops the column once the
role is authoritative. The bootstrap admin (slice 1 `auth.bootstrap_admin`) is
assigned the `admin` role on first run instead of (or in addition to) setting
`is_admin`.

#### Anonymous as a role

`Anonymous(ctx)` principals are evaluated against the built-in `anonymous` role's
grants only. `auth.anonymous_mode` (slice 1: `off`/`allowlist`/`all`) still controls
**whether** a request becomes `Anonymous` at all; RBAC then decides **what** that
anonymous principal can do. The migration seeds the `anonymous` role with `read`
grants for each repo that had `anonymous_read = true`. Admins manage anonymous
access going forward by editing the `anonymous` role's grants (e.g. add a content
selector to expose only public packages from an otherwise-private repo — a feature
slice 1 could not express).

#### Per-token scoping

On token creation (admin API or §12.2 user self-service), an optional `scope` JSON
is stored. At auth time the principal carries its `token_id`; the evaluator loads
the token scope and computes `effective = owner_effective ∩ scope`. Validation at
creation: the scope's actions/repos must be a **subset** of the owner's *current*
grants (best-effort — owner grants can later shrink, in which case intersection
naturally shrinks the token too; a token can never out-grant its live owner). A
revoked/expired token is rejected before RBAC runs (slice-1 behavior, unchanged).

### Replacing the slice-1 coarse checks (seam integration)

Slice 1's coarse logic (illustrative):

```rust
// BEFORE (slice 1, in core::authz)
pub fn can_read(p: &Principal, repo: &Repository) -> bool {
    match p {
        Principal::User(_) => true,
        Principal::Anonymous(_) => repo.anonymous_read,
    }
}
pub fn can_write(p: &Principal, _repo: &Repository) -> bool {
    matches!(p, Principal::User(_))
}
pub fn can_admin(p: &Principal) -> bool {
    matches!(p, Principal::User(u) if u.is_admin)
}
```

After this slice, the same functions delegate to the cached evaluator. **Call sites
do not change**; only the bodies and the async-ness (they become `async` because
they hit the cache/DB on a cold L1 — flagged below):

```rust
// AFTER (core::authz) — signatures preserved; now async + take the evaluator
pub async fn can_read(authz: &Authz, p: &Principal, repo: &Repository) -> Result<bool, AuthzError> {
    let eff = authz.effective(p).await?;            // cached, see §caching
    Ok(eff.is_admin || eff.allows_repo(Action::Read, repo.id))
}
pub async fn can_write(authz: &Authz, p: &Principal, repo: &Repository) -> Result<bool, AuthzError> {
    let eff = authz.effective(p).await?;
    Ok(eff.is_admin || eff.allows_repo(Action::Write, repo.id))
}
pub async fn can_admin(authz: &Authz, p: &Principal) -> Result<bool, AuthzError> {
    let eff = authz.effective(p).await?;
    Ok(eff.is_admin)                                 // privilege-mgmt endpoints
}

// New, for package-scoped responses:
pub async fn package_filter(authz: &Authz, p: &Principal, repo: &Repository)
    -> Result<PackageFilter, AuthzError> { /* compiled GlobSet predicate, or AllowAll */ }
```

`EffectiveSet` (the cached value) is a compact, owned structure:

```rust
pub struct EffectiveSet {
    pub is_admin: bool,
    // per (action) → list of (repo_id|ANY, optional compiled selector)
    grants: Vec<Grant>,            // small; ANY collapses many repos
}
struct Grant { action: Action, repo: Option<i64>, selector: Option<Arc<CompiledSelector>> }
struct CompiledSelector { includes: GlobSet, excludes: GlobSet }
```

**Seam wiring notes / flagged assumptions:**
- *`can_read` becoming `async`*: slice-1 group resolution and route handlers must
  `await` it. If slice 1 made `can_read` sync, Phase 1 audits call sites and makes
  them async (they are already in async axum handlers, so this is mechanical). If
  any sync caller exists in a non-async context, it uses `Authz::effective_blocking`
  off a cached value. **Flagged.**
- The evaluator is a single `Authz` service constructed in `server` wiring with a
  `db::Pool` + `cache::Cache` handle and injected into request extensions /
  `core` operations, mirroring how slice 1 injects its DB/cache handles. **Flagged
  assumption: there is a place to add an app-state field.**

### The effective-set query (single round trip)

Cold-cache load for a user principal:

```sql
-- $1 = user_id
SELECT
  EXISTS (SELECT 1 FROM user_role ur JOIN role r ON r.id = ur.role_id
          WHERE ur.user_id = $1 AND r.name = 'admin')               AS is_admin,
  rp.repository_id, rp.action,
  cs.includes, cs.excludes
FROM user_role ur
JOIN repository_privilege rp ON rp.role_id = ur.role_id
LEFT JOIN content_selector cs ON cs.id = rp.selector_id
WHERE ur.user_id = $1;
```

For anonymous: same query against the fixed `anonymous` role id (no user join).
Token scoping is applied in Rust by intersecting the loaded set with the token's
`scope`. Selector globs are compiled once when the `EffectiveSet` is built and held
behind `Arc` so cache entries are cheap to clone.

### Permission caching + cross-instance invalidation

Reuse the slice-1 `cache` crate (L1 moka + optional Redis L2 + pub/sub
invalidation backplane). We cache the **`EffectiveSet`**, not individual decisions:

- **Cache key** (versioned to allow blanket invalidation):
  - user: `authz:v1:user:{user_id}` (scope is applied *after* the cached owner set,
    so the owner set is shared across that user's tokens).
  - anonymous: `authz:v1:anon` (single shared entry; selectors live inside it).
- **Lookup**: `cache.try_get_with(key, factory)` — L1 → L2 → `factory` (the SQL
  above). Per-instance stampede protection via moka `try_get_with`; the load is
  cheap enough that no cross-instance advisory lock is needed (unlike proxy
  fetches).
- **TTL**: short default (e.g. 60s) so that even without Redis, staleness after a
  privilege change is bounded — fail-safe given the explicit invalidation below.
- **Explicit invalidation (authoritative)**: every mutation that affects authz
  publishes an invalidation on the backplane and drops local L1:
  - editing a `role`'s grants / selectors → invalidate **all** principals that hold
    that role. Cheapest correct approach: bump a **global authz epoch** key
    (`authz:epoch`) that is part of every cache key's namespace, so any role/grant
    change blanket-invalidates by rolling the epoch. (Coarse but always-correct and
    O(1) to publish; the alternative — enumerating affected users — is an
    optimization we can add if epoch churn is too aggressive. **Decision: ship the
    epoch, measure, optimize later.**)
  - `user_role` change for user U → invalidate `authz:v*:user:{U}` (targeted).
  - token `scope`/revoke change → token scope is applied post-cache, so revocation
    is already handled by the slice-1 token check; a scope edit invalidates nothing
    cached (re-read of token row on next request). Token row reads themselves may be
    cached by slice 1 — if so, that cache is invalidated on scope/revoke by slice-1
    machinery; **flagged** to confirm.
  - `repository` delete cascades grants (FK `ON DELETE CASCADE`) → roll epoch.
- **Why epoch + short TTL is fail-closed-enough**: a *grant removal* must not keep
  letting a revoked principal in. The epoch roll makes every instance recompute on
  the next request (L1/L2 miss → fresh SQL), and the short TTL is the backstop if a
  backplane message is lost. Privilege *removal* therefore takes effect within
  `min(backplane latency, TTL)`; for revocation-sensitive flows (token revoke) the
  slice-1 token check is the authoritative immediate gate.

### Nested-group resolution + cycle detection

Slice 1 forbade nested groups (`member_id` must be hosted/proxy). This slice lifts
that and makes nesting safe:

- **Config-time guard (admin API, fail-closed):** when adding/updating a
  `group_member` edge `(group_id=G, member_id=M)`, if `M` is itself a group, run a
  reachability check: *does `G` appear in the transitive members of `M`?* If yes →
  **reject 409** (would create a cycle). Also enforce a configurable
  **`groups.max_nesting_depth`** (default e.g. 20): reject if adding the edge makes
  any path exceed it. Implemented as a recursive CTE:

  ```sql
  -- would adding (G -> M) create a cycle? cycle iff G is reachable from M.
  WITH RECURSIVE reach(id, depth, path) AS (
      SELECT $M::bigint, 0, ARRAY[$M::bigint]
    UNION ALL
      SELECT gm.member_id, reach.depth + 1, reach.path || gm.member_id
      FROM group_member gm
      JOIN reach ON gm.group_id = reach.id
      WHERE NOT gm.member_id = ANY(reach.path)        -- stop on revisit (defensive)
        AND reach.depth < $max_depth
  )
  SELECT EXISTS (SELECT 1 FROM reach WHERE id = $G) AS would_cycle,
         COALESCE(MAX(depth), 0) >= $max_depth        AS too_deep
  FROM reach;
  ```

  The edge insert and this check run in **one transaction** (`SELECT ... ` then
  `INSERT` with the row-level lock / `SERIALIZABLE`-or-advisory-lock on the group
  graph) so two concurrent edge inserts can't race a cycle into existence across
  instances. **(Decision: take a Postgres advisory lock keyed on a constant
  "group-graph" id for the duration of any group-edge mutation — group edits are
  rare, so a global lock is fine and removes the concurrent-insert race entirely.)**

- **Resolve-time guard (defense in depth, fail-closed):** group resolution becomes
  a DFS/BFS over `group_member` that flattens nested groups into the ordered list of
  **leaf** (hosted/proxy) members, applying the slice-1 priority ordering at each
  level. It carries a **`visited: HashSet<repo_id>`** and a **depth bound**; if a
  back-edge or the depth bound is hit, it **logs an error and treats the offending
  subtree as empty** (fail-closed: serve nothing from the cyclic branch rather than
  loop forever). This guarantees termination even if a cycle somehow slipped past
  the config guard (e.g. via a direct DB write).
- **Identity-aware filtering now honors privileges:** the slice-1 rule
  `visible = [m for m in members if can_read(P, m)]` is preserved but `can_read`
  now consults RBAC (not `anonymous_read`). The flatten step filters at **every
  level** — a principal who cannot read an inner group's member never sees its
  packages. Concretely: resolution descends only into members the principal
  `can_read`, and a leaf member is included only if `can_read(P, leaf)`. Ordering
  across nesting levels: the resolved leaf order is a stable pre-order walk honoring
  each group's `priority` (higher wins, slice-1 rule), with the flattened order used
  for "highest-priority member that has it" download resolution.
- **Cycle-detection ordering note (CTE `path` vs. priority):** the recursive CTE
  uses `path` only to break cycles defensively; the *priority* ordering is applied
  by the resolver in Rust (or an `ORDER BY` on the flatten query) so the
  deterministic-priority guarantee from slice 1 is retained.

### Admin endpoints (privilege management)

All under the existing admin API, gated by `can_admin` (i.e. `admin` role). REST,
mirroring slice-1 admin conventions:

- `POST/GET/PATCH/DELETE /admin/roles` (+ `/{id}`) — CRUD roles (builtin roles:
  PATCH allowed for non-`admin`/non-`anonymous` grants only; DELETE forbidden).
- `PUT/DELETE /admin/roles/{id}/grants` — add/remove a `repository_privilege`
  `(repo|ANY, action, selector?)`.
- `GET/PUT/DELETE /admin/users/{id}/roles` — assign/unassign roles.
- `POST/GET/PATCH/DELETE /admin/content-selectors` (+ `/{id}`).
- `PATCH /admin/repositories/{id}/members` — group membership edits run the
  config-time cycle/depth guard; `409` on cycle/too-deep.
- Token scope: `POST /admin/users/{id}/tokens` (and the §12.2 self-service path)
  accept an optional `scope`; `PATCH /admin/tokens/{id}/scope`.
- `GET /admin/users/{id}/effective` — debug/explain endpoint returning the computed
  `EffectiveSet` (admin-only; invaluable for support and for the test matrix).

Every mutating endpoint publishes the appropriate cache invalidation (targeted
user invalidation or epoch roll) **after** its transaction commits.

- **Test:** existing slice-1 authz unit/e2e tests still pass unchanged (the

  `allows_repo` and the package-filter predicate. **No cache yet** — every call hits

  - principal × repo × action **matrix**: admin-role allows all; a role with

    grant exists; package filter hides non-matching packages.
  - anonymous role evaluation.

- **What:** `Authz::effective(principal)` does cached L1→L2→SQL load; apply token
  scope intersection post-load; admin short-circuit. Seam functions delegate.
- **Tests:**
  - `crates/core/src/authz/cache.rs`: L1 hit avoids DB (mock/counted pool); epoch
    roll forces reload; targeted user invalidation drops only that user's entry;
    TTL expiry reload.
  - token scoping unit test: owner has `(read,write on repoA)`, token scope
    `{actions:[read], repositories:[repoA]}` ⇒ token may read A, may **not** write A.
    Scope can't widen: owner lacks repoB ⇒ token scoped to repoB still denied.
  - re-run the Phase 2 matrix through the cached seam → identical results.

### Phase 4 — Nested groups + cycle detection
- **Files:** `crates/db/src/groups.rs` (the recursive-CTE reachability/depth check,

  `visited`+depth, per-level `can_read` filtering, priority ordering);
  `crates/server/src/admin/members.rs` (member-edit endpoint runs the config guard).
- **What:** lift the slice-1 "no nested groups" rule; add config-time cycle/depth
  rejection under the group-graph advisory lock; add resolve-time fail-closed guard;
  rewire identity-aware filtering to RBAC `can_read`.
- **Tests:**
  - config-time: adding an edge that closes a cycle ⇒ `409`; exceeding
    `max_nesting_depth` ⇒ `409`; valid nesting ⇒ accepted.
  - resolve-time: a manually-injected DB cycle terminates (fail-closed, empty
    cyclic subtree, error logged) — does not hang.
  - nested visibility: principal that can read inner group G2 but not its sibling
    member sees only what RBAC permits; anonymous sees only `anonymous`-role-granted
    leaves through nesting.

### Phase 5 — Data migration: preserve slice-1 behavior, flip defaults safely
- **Files:** `migrations/00XX_rbac_migrate_admins.sql`,
  `migrations/00XX_rbac_migrate_anonymous.sql`, plus a guarded code path in
  `crates/db` bootstrap.
- **What (in one logical migration, idempotent):**
  - For every `app_user.is_admin = true` → insert `user_role(user_id, admin_role)`.
  - For every `repository.anonymous_read = true` → insert
    `repository_privilege(anonymous_role, repository_id, 'read')`.
  - **Preserve slice-1 "any authenticated user can read/write"**: assign the
    `authenticated` builtin role to **every existing `app_user`**, and seed it with
    `(read, ANY)` + `(write, ANY)` grants. This makes the post-migration behavior
    *identical* to slice 1 for existing users (they keep working). New deployments
    can later strip those `authenticated` grants to lock things down. A config flag
    `auth.legacy_open_access` (default **true** on upgrade, **false** on fresh
    install) controls whether new users are auto-assigned `authenticated`. **This is
    the safe default-flip:** upgrades stay open (no surprise lockouts), fresh
    installs are closed (secure by default).
  - Bootstrap admin assignment moves to granting the `admin` role.
- **Dual-read window:** evaluator's admin check = `in_admin_role OR is_admin`;
  read/write fall back to nothing extra (the `authenticated` grants cover the old
  behavior). A **follow-up migration** (out of this slice or end of it) drops
  `is_admin` and `anonymous_read` once verified.
- **Tests (e2e, testcontainers):**
  - upgrade simulation: seed a slice-1-shaped DB (users with `is_admin`,
    repos with `anonymous_read`), run migrations, assert: admins still admin,
    anonymous still reads the same repos, ordinary users still read/write
    everywhere (legacy open). Then flip `legacy_open_access` off + strip
    `authenticated` grants → a user with no roles is denied (fail-closed).

- **Files:** `crates/server/src/admin/roles.rs`, `.../grants.rs`,

- **Token scoping** — a `read`-only scoped token can restore but a push returns 403;
  a token scoped to repoA cannot touch repoB.

  without it, anonymous gets 401/403 per `anonymous_mode`; anonymous + content

  ⇒ request completes (fail-closed empty subtree), server logs error, **no hang**

## 6. Security & failure modes

- **Fail-closed by default.** No matching grant ⇒ deny. There are no explicit-deny
  rows (additive grant-only model), so there is no deny-vs-allow precedence bug
  surface. A fresh install (`legacy_open_access = false`) denies everything until an
  admin grants; an upgrade preserves slice-1 openness explicitly and visibly.
- **Privilege escalation vectors & mitigations:**
  - *Token can't out-grant owner* — scope is an intersection computed live against
    the owner's current set; shrinking owner grants shrinks the token automatically.
  - *Builtin-role tampering* — `admin`/`anonymous` roles are `builtin`; API forbids
    deleting them and restricts dangerous edits; the `admin` short-circuit is
    membership-based, so you cannot escalate by editing the `admin` role's grant
    rows.
  - *Selector bypass* — repo-level gate vs. package-filter split is deliberate:
    a selector-scoped `read` grant lets you reach the repo but the package filter is
    re-applied on **direct download** (not only on listings), so you can't fetch a
    package the selector excludes by guessing its URL. Excluded/forbidden direct
    download returns **404**, not 403, to avoid leaking package existence.
  - *Group nesting as a read-amplifier* — identity-aware filtering is applied at
    **every nesting level**, so you cannot gain read to an inner member by being
    granted read to an outer group. Group membership grants **no** transitive
    package read on its own; only `read` grants on the actual member repos do.
- **Cache staleness after revocation.** Privilege *removal* is the dangerous
  direction. Mitigations: explicit backplane invalidation (epoch roll) on every
  mutation + short L1/L2 TTL backstop (correct even if a backplane message is lost or
  Redis is absent). For the most time-sensitive case — **token revocation** — the
  authoritative slice-1 token check (revoked/expired ⇒ reject) runs *before* RBAC and
  is not subject to the RBAC cache, so a revoked token dies immediately cluster-wide.
  Documented residual: a *grant* removal (not a token revoke) may linger up to
  `min(backplane latency, TTL)`; this is the standard distributed-cache tradeoff and
  is bounded and tunable via `cache.default_ttl`.
- **Cycle-induced infinite loops.** Two independent guards: config-time rejection
  under a group-graph advisory lock (prevents creation, race-free across instances)
  and resolve-time `visited`-set + depth bound (terminates even on a cycle injected
  by raw DB write). Resolution is **bounded** (`groups.max_nesting_depth`) and
  **fail-closed** (cyclic subtree treated as empty, error logged).
- **DoS via deep/wide nesting** — `max_nesting_depth` caps recursion depth; the
  flatten query is bounded; results are cacheable. Group edits are rare and serialized
  by the advisory lock.
- **Performance / hot path.** The repo-level gate is an in-memory set test over the
  cached `EffectiveSet` (no DB on warm cache). Selector globs are precompiled
  (`GlobSet`) and shared via `Arc`. Cold load is a single indexed SQL query. This
  keeps download/restore latency dominated by S3, not authz.

## 7. Open questions / risks

1. **Role nesting (roles that contain roles).** Nexus supports it; we deliberately
   ship flat roles to keep the evaluator a single join. If demand appears, add a
   `role_member(parent_role_id, child_role_id)` table with the *same* cycle-detection
   machinery built here for groups — the algorithms transfer directly. Risk:
   retrofitting changes the effective-set query to a recursive CTE.
2. **Selector expression language.** We pick **globs** (JFrog/Ant-like) over Nexus's
   CSEL/JEXL for simplicity. Open: do we also need version-range selectors (e.g.
   "read only prereleases" / "only `>= 2.0`")? Deferred; the `content_selector`
   schema can grow a `version_range` column without breaking existing rows.
3. **Interaction with §12.1 retention selectors.** §12.1 may want to express "this
   retention policy targets packages matching X." That is a *different* selector
   (lifecycle, not authz). Risk of two divergent selector DSLs. **Proposed
   resolution:** if §12.1 lands after this, it should reuse the `content_selector`
   *table + glob compiler* (shared `CompiledSelector`) but reference it from
   `retention_policy`, keeping authz and lifecycle decisions separate while sharing
   the matching engine. Flagged for whichever slice lands second.
4. **Interaction with §12.2/§12.3 identity sources.** Those slices decide *who* a
   user is and may want **claim-/group-driven role assignment** (e.g. Entra group →
   forge role). This slice exposes the seam ("given `user_id`, which roles?") and the
   `user_role` table they will populate, plus the admin API to manage roles. Open:
   whether external-group→role mapping is stored as auto-managed `user_role` rows
   (simple, reuses invalidation) or a separate mapping table evaluated at login
   (avoids stale rows when group membership changes). **Recommendation:** §12.2/12.3
   write `user_role` rows at login and invalidate that user's authz cache — reuses
   everything here. Risk: de-provisioning lag if claims aren't re-read.
5. **Epoch-roll invalidation granularity.** Rolling a global epoch on any
   role/grant edit is always-correct but invalidates *every* principal's cache. If
   role edits turn out frequent, switch to enumerating affected users (join
   `user_role`) for targeted invalidation. Decision: ship epoch, measure, optimize.
6. **`can_read` becoming `async`.** If any slice-1 caller is in a sync context, it
   needs refactoring (expected to be none — all callers are async axum handlers /
   async core ops). Flagged for the Phase 0 audit.
7. **Confirming the principal carries `token_id`.** Per-token scoping requires it;
   if slice 1 discards the token id after lookup, the principal middleware needs a
   one-line change. Flagged for Phase 0.
