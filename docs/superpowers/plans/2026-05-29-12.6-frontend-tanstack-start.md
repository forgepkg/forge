# Frontend (TanStack Start admin + browse UI) — Design & Implementation Plan

**Date:** 2026-05-29
**Slice:** §12.6 of the `envisia-forge` design (depends on the approved Slice 1 spec,
`2026-05-29-envisia-forge-nuget-design.md`; soft-depends on §12.2 sessions and §12.4 RBAC)
**Status:** Draft — forward-looking plan

## Goal

Ship a **TanStack Start** web UI that lets administrators **manage** the registry
(create/edit hosted/proxy/group repositories, edit group members + priority,
manage users and tokens) and lets any reader **browse and search** packages
across repositories, **view package detail** (versions, dependencies, download
stats), and **see package-delay / retention status**. The browser must call the
**Rust HTTP API directly** — there is **no Node→Rust API proxy** (slice-1 hard
constraint §1, §12.6). The frontend serves UI only; all data comes from the
slice-1 `server` crate's admin REST API plus a small read-side extension defined
here.

## Architecture (overview)

The Rust `server` crate serves the **built static frontend assets** (and the SPA
shell) from a configured directory, so the UI and the API live on a **single
origin** — no CORS, no proxy, satisfying the no-Node-proxy rule. We ship the UI
in **SPA mode** (TanStack Start / Router with client-side rendering and a static
`index.html` shell), not full SSR, because SSR would require a Node server to
data-fetch from Rust per request — re-introducing exactly the Node API surface
the constraint forbids. The browser uses **TanStack Query** against a single
configurable API base URL (same origin), sending the slice-1 token via header or
(post-§12.2) the session cookie automatically. In dev, **Vite** serves
assets/HMR and forwards only **non-API** unmatched routes to its own SPA shell
while the browser still hits the Rust `server` for `/v3/*`, `/admin/*`, `/auth/*`
— Vite never proxies API calls (it may optionally proxy them to Rust purely as a
dev convenience, see §Dev mode; it is never a production code path).

## Dependencies

- **Slice 1 merged.** We consume the slice-1 `server` admin REST API
  (repositories / members / users / tokens CRUD), the `token` model, the
  principal-extraction middleware, and `server.public_base_url`.
- **New read-side endpoints** in the slice-1 `server` crate (browse/search/stats),
  specified concretely in §Design → *Additional Rust `server` API*. These are
  additive and admin-or-reader gated; they do not change slice-1 write paths.
- **Soft dependency — §12.2 OIDC sessions** for the production **login UX**
  (cookie session). Until §12.2 lands, the UI authenticates with a manually
  pasted **token** (the slice-1 model) stored client-side; the auth layer is
  written so swapping token-header for cookie-session is a one-module change.
- **Soft dependency — §12.4 RBAC** for *what the UI shows per role*. Until §12.4
  lands, authz is binary (`is_admin` ⇒ management screens visible; everyone else
  ⇒ browse/search only), matching slice-1 §5. The UI reads capability flags from
  a `/admin/me` endpoint so RBAC can later refine them without UI rewrites.

## Tech stack

- **TanStack Start + TanStack Router** — virtual file routes (routes declared in
  `src/routes.ts`, generated into `routeTree.gen.ts`; never hand-author route
  files). Run in **SPA mode**.
- **TanStack Query** — all server state / caching / invalidation. No hand-rolled
  `useEffect` + `fetch`.
- **Vite (Rolldown-Vite)** — dev server + production static build.
- **Styling: Tailwind CSS** (chosen). Justification: zero-runtime, single small
  CSS bundle ideal for a static-asset deployment the Rust server embeds; no CSS-in-JS
  runtime to ship; utility classes keep the component count low for an
  admin tool. (Bootstrap would pull a larger baseline; CSS-in-JS adds runtime
  weight that fights the single-origin/static-asset goal.) Use `clsx` for
  conditional classes; no inline `style`.
- **Vitest + React Testing Library** for unit/component tests; **Playwright** for
  e2e against the Rust `server` serving the built UI.
- **Forms:** React Hook Form. **Tables/pagination:** TanStack Table (headless).

## Scope

**In scope**

- SPA served by the Rust `server` at a single origin; SPA fallback routing.
- Token-based auth in the browser today; cookie-session-ready auth layer for §12.2.
- Admin screens: repositories list/create/edit (hosted/proxy/group), group
  member + priority editor, users CRUD + activate/deactivate, token list /
  create (show-once secret) / revoke.
- Browse: cross-repository package list + search; package detail (versions,
  dependencies, download stats, package-delay/retention status badges).
- The additive read-side Rust `server` endpoints needed by browse/search/stats.
- Dev-mode Vite setup; production build pipeline producing assets the Rust server
  serves.
- Unit/component tests + e2e against the slice-1 harness (Postgres + versitygw).

**Explicitly out of scope**

- Implementing OIDC login itself (that is §12.2; this slice only consumes its
  session cookie when present).
- Implementing RBAC role/privilege management screens (that is §12.4; this slice
  shows admin-vs-not and reads capability flags).
- Retention **policy editing** UI beyond *displaying* status (policy CRUD belongs
  with §12.1; here we only render the delay/retention status the API reports).
- Server-side rendering / Node runtime in production. SSR is rejected (see Design).
- Any Node-hosted API surface, BFF, or proxy in front of Rust.
- Multi-format UI specialization (only NuGet exists in slice 1).

## Design

### 1. Serving / deployment model (recommendation: SPA mode, Rust-served, single origin)

**Recommendation:** build the TanStack Start app in **SPA mode** and have the Rust
`server` crate serve the resulting static assets. Rationale:

- Full SSR needs a long-lived **Node** process that, per request, fetches data
  from the Rust API to render HTML. That Node process *is* a server-side API
  consumer in front of Rust — it doesn't proxy the browser's calls, but it
  re-introduces a Node tier that has to be deployed, scaled, and kept in sync with
  the Rust API, and any "give the page its data" helper trivially becomes a thin
  re-export of the Rust API (the exact anti-pattern §12.6 forbids). SPA mode has
  **no Node runtime in production**: ship static files, the browser does all
  data-fetching directly against Rust. This is the cleanest satisfaction of the
  constraint.
- SEO/first-paint are non-concerns for an authenticated admin/registry tool.

**How Rust serves it.** Add to the slice-1 `server` crate a static-asset layer
mounted **after** all API routers (`/v3/*`, `/admin/*`, `/auth/*`), so API paths
always win and only genuine UI paths fall through:

```rust
// crates/server/src/web_ui.rs (new) — illustrative
use tower_http::services::{ServeDir, ServeFile};

/// Serve the built SPA from `cfg.web.assets_dir`, falling back to index.html
/// for client-side routes (SPA history fallback). Mounted LAST so API wins.
pub fn web_ui_router(cfg: &WebUiConfig) -> axum::Router {
    let index = cfg.assets_dir.join("index.html");
    let serve_dir = ServeDir::new(&cfg.assets_dir)
        .not_found_service(ServeFile::new(index)); // SPA fallback
    axum::Router::new().fallback_service(serve_dir)
}
```

Wiring in the existing app builder:

```rust
// crates/server/src/app.rs — add after admin/v3/auth routers are merged
let app = app
    .merge(admin_api_router(state.clone()))
    .merge(nuget_v3_router(state.clone()));
let app = match &cfg.web {
    Some(web) if web.enabled => app.merge(web_ui_router(web)),
    _ => app, // headless deployment: no UI served
};
```

- **Embed vs. directory.** Two supported modes via config:
  `web.assets_dir = "/path"` (operator-supplied dir, default in container images),
  **or** `web.embed = true` to compile assets into the binary with
  `rust-embed`/`include_dir` behind a `web-ui` cargo feature for a single-binary
  deploy. Recommend **directory by default**, embed as an opt-in feature so the
  headless build stays small. The UI build artifact is the only coupling.
- **SPA fallback correctness.** `ServeDir` returns real files when they exist
  (`/assets/app-*.js`), and `index.html` for unknown paths (`/repositories/foo`)
  so TanStack Router resolves client-side. A request to `/admin/...` never reaches
  this fallback because the admin router is merged first and matches.
- **`server.public_base_url`** (slice 1) remains the canonical absolute base the
  SPA reads at runtime (see auth/config below) — the API and UI share it.

### 2. Dev mode (Vite dev server; API still goes to Rust)

In development the two run side by side:

- `cargo run -p server` on, say, `http://localhost:8080` (real API + Postgres +
  versitygw via the slice-1 harness or a local stack).
- `vite dev` (TanStack Start dev) on `http://localhost:3000` serving the SPA
  shell + HMR.

The browser's API base URL in dev is set to the Rust origin
(`VITE_FORGE_API_BASE=http://localhost:8080`) so **API calls go straight to Rust**.
This is cross-origin in dev only; the Rust `server` enables a **dev-only CORS
allowlist** (`auth`/`web.dev_cors_origins`, empty/disabled in prod) for
`http://localhost:3000`. Because prod is single-origin, prod ships **no CORS**.

Optionally, to keep dev single-origin too, Vite's `server.proxy` may forward
`/admin`, `/v3`, `/auth` to the Rust server. **This is a dev-only static-routing
convenience, not an API proxy in the architectural sense** — it forwards verbatim,
adds no logic, and has no production equivalent (prod is single-origin via Rust
`ServeDir`). Prefer this proxy form so dev and prod use **relative** API URLs and
the CORS path is never exercised. (Document both; recommend the Vite-proxy form.)

### 3. Auth / session handling in the browser

Single auth module (`src/lib/auth.ts`) abstracts credential acquisition so the
slice-1 token model and the §12.2 cookie session are interchangeable:

- **Today (slice 1, token):** user pastes a registry token (created in the Tokens
  screen or out-of-band). Stored in `localStorage` (admin tool, acceptable) and
  attached as `Authorization: Basic base64("token:" + secret)` **or**
  `X-NuGet-ApiKey` — slice-1 §5 accepts a token as the Basic secret, so we use
  Basic for admin API calls (the admin API expects Basic per §5/§8). A single
  `httpClient` wrapper injects the header.
- **Post-§12.2 (session cookie):** when a session cookie is present the browser
  sends it automatically (`fetch`/Query with `credentials: "include"`, or simply
  same-origin in prod). The auth module detects "have cookie session" by calling
  `GET /admin/me`; if it returns `200`, no header is attached and the cookie
  governs. The login screen then becomes "Sign in with OIDC" (redirect to
  `/auth/oidc/login`, a §12.2 route) instead of "paste a token".
- **401 handling:** a Query/`fetch` `401` clears stored credentials and routes to
  `/login`. A global Query `onError`/retry policy treats `401`/`403` as
  non-retryable.
- **Capability flags:** `GET /admin/me` returns `{ user, is_admin, capabilities }`.
  The router uses `is_admin` (and later §12.4 `capabilities`) to gate management
  routes via `beforeLoad` redirects; the nav renders only permitted links.

### 4. Information architecture / screen list

```
Public-ish (any reader / anonymous per repo.anonymous_read):
  Browse              — cross-repo package search + list
  Package detail      — versions, dependencies, download stats, delay/retention status
  Repository overview — read-only repo info (kind, online, anonymous_read, members)

Admin (is_admin; later §12.4-scoped):
  Repositories        — list / create (hosted|proxy|group) / edit / delete
    └ Group editor     — add/remove members, set priority (unique per group)
    └ Proxy config     — remote_url, package_delay, ttls, upstream creds (write-only)
  Users               — list / create / edit / activate-deactivate
  Tokens              — list (own + per-user for admin) / create (show-once) / revoke

Auth:
  Login               — token paste (now) → OIDC redirect (§12.2)
```

### 5. Route tree (virtual file routes — declared in `src/routes.ts`)

```ts
// src/routes.ts (TanStack virtual file routes — do NOT hand-author route files)
export const routes = rootRoute('root.tsx', [
  route('/login', 'Login.tsx'),
  layout('app', 'AppLayout.tsx', [               // nav shell + auth context
    index('Browse.tsx'),                          //  /            browse+search
    route('/packages/$repo/$id', 'PackageDetail.tsx'),
    route('/repositories', 'repositories/RepositoriesRoot.tsx'), // read overview
    route('/admin', '_admin.tsx', [               // beforeLoad: require is_admin
      route('/repositories', 'admin/repositories/List.tsx'),
      route('/repositories/new', 'admin/repositories/Create.tsx'),
      route('/repositories/$repo', 'admin/repositories/Edit.tsx', [
        route('/members', 'admin/repositories/GroupMembers.tsx'), // group only
      ]),
      route('/users', 'admin/users/List.tsx'),
      route('/users/$userId', 'admin/users/Edit.tsx'),
      route('/tokens', 'admin/tokens/List.tsx'),
    ]),
  ]),
]);
```

`_admin.tsx` is a pathless layout whose `beforeLoad` calls the `me` query and
redirects non-admins to `/`. Browse/detail are reachable without admin.

### 6. Component boundaries

- **`src/lib/`** — cross-cutting, no JSX: `httpClient.ts` (fetch wrapper +
  auth header injection + base URL), `auth.ts` (credential store + `me`),
  `config.ts` (reads `import.meta.env.VITE_FORGE_API_BASE`, defaults to relative
  `""` for single-origin prod).
- **`src/api/`** — one module per resource (`repositories.ts`, `users.ts`,
  `tokens.ts`, `packages.ts`, `me.ts`): typed request functions + **query-key
  factories** + typed response interfaces mirroring the Rust DTOs.
- **`src/queries/`** — TanStack Query hooks (`useRepositories`, `useRepository`,
  `useCreateRepository`, `usePackageSearch`, `usePackageDetail`, `useMe`, …)
  wrapping `src/api/`.
- **`src/routes/`** — route components only (data-loading via the query hooks,
  layout, forms). Thin; delegate to feature components.
- **`src/components/`** — reusable presentational pieces: `RepoKindBadge`,
  `PriorityList` (DnD-free ordered list with up/down + number input),
  `VersionTable`, `DependencyGroups`, `DelayBadge`, `RetentionBadge`,
  `ShowOnceSecret`, `Paginator`, `SearchBox`, `ErrorState`, `EmptyState`.

### 7. Data-fetching / query-key conventions

- Query keys are arrays from a per-resource factory:
  `repoKeys.list(filters)`, `repoKeys.detail(name)`, `pkgKeys.search(params)`,
  `pkgKeys.detail(repo, id)`, `tokenKeys.list(userId)`, `meKeys.self()`.
- Reads use `useQuery` (not `useSuspenseQuery` at the top app level, to keep the
  401→login redirect simple); list screens use `placeholderData: keepPreviousData`
  for pagination.
- Mutations (`useMutation`) invalidate the relevant list/detail keys on success
  and surface errors to the form. Token creation returns the **plaintext once**
  and is rendered via `ShowOnceSecret`; it is never re-fetched.
- All calls go through `httpClient` so the auth header / `credentials: include`
  and base URL are centralized; switching to cookie-session touches only that file.

### 8. Additional Rust `server` API endpoints (read-side, additive)

These extend the slice-1 admin API in the **`server` crate**. They reuse slice-1
authz: browse/search/stats honor `can_read` (anonymous allowed iff
`repository.anonymous_read`), management endpoints (already in slice 1) require
`is_admin`. Responses are JSON DTOs (not the NuGet V3 protocol shapes — the UI
uses these instead of scraping `/v3/*`). All list endpoints are paginated
(`skip`, `take`, returning `{ total, items }`).

- **`GET /admin/me`** → `200 { "user": {"id","username","is_admin","active"}, "is_admin": bool, "capabilities": ["repo.read","repo.admin",…] }`; `401` if no/invalid principal (browse-only anonymous returns `{ "user": null, "is_admin": false, "capabilities": ["repo.read"] }`). Drives nav + route gating.
- **`GET /admin/repositories`** (already in slice-1 admin API; relied on here) → `200 { total, items:[ {id,name,kind,format,online,anonymous_read,member_count?} ] }`.
- **`GET /admin/repositories/{name}`** (slice-1) → repo detail incl. kind-specific config; proxy `upstream_password` **redacted** (slice-1 §5), group includes ordered members `[{member_id,member_name,priority}]`.
- **`GET /browse/packages`** *(new)* — cross-repository search.
  - Query: `q`, `repo` (optional filter), `prerelease` (bool), `skip`, `take`.
  - `200 { total, items:[ { repo, id, original_id, latest_version, listed, total_downloads, repo_kind } ] }`.
  - Honors `can_read` per repo; group repos resolve to visible members (slice-1
    identity-aware group resolution); package-delay-gated proxy versions are
    excluded (slice-1 §7). Implemented over Postgres `component` /
    `proxy_cached_version` (not by calling `/v3/*`).
- **`GET /browse/packages/{repo}/{id}`** *(new)* — package detail.
  - `200 { repo, id, original_id, repo_kind, versions:[ { version, version_original, listed, size, published_at, downloads, delay_status: "available"|"delayed_until"|null, delayed_until?: ts, retention_status?: "kept"|"pending_prune"|null } ], dependency_groups_by_version: { "<version>": [ {target_framework, dependencies:[{id,range}]} ] } }`.
  - `delay_status`/`delayed_until` from `proxy_cached_version.first_seen_at +
    package_delay_seconds` for proxy repos (slice-1 §7). `retention_status` is
    `null` until §12.1 lands (field reserved now so the UI is forward-compatible).
- **`GET /browse/packages/{repo}/{id}/stats`** *(new, optional split)* — download
  stats time series if the detail payload grows large: `200 { total_downloads, by_version:[{version,downloads}], series?:[{date,downloads}] }`. (Slice 1 stores download counts where available; `series` is reserved/empty until a counters slice lands — flag as assumption: slice-1 has per-version download counts but not necessarily a time series.)

> **Assumption flags about unbuilt internals:** (a) slice-1 stores per-version
> download counts somewhere queryable (the search JSON shows `downloads`); if it
> only stores aggregate, `by_version`/`series` degrade to `total_downloads`.
> (b) `published_at` maps to `component.created_at`. (c) The slice-1 admin
> repository CRUD endpoints exist with the request/response shapes implied by
> §3/§8; this plan's frontend `src/api/repositories.ts` types must be reconciled
> against the real slice-1 DTOs when slice 1 is merged.

Frontend lives in a new top-level dir **`web/`** (sibling to `crates/`), built by
Vite; the Rust `server` consumes `web/dist/`. TDD-ish: component/integration tests
land with each phase; e2e last.

## Testing

**Unit / component (Vitest + React Testing Library)** — per phase above:
auth header injection + 401 handling; nav/route admin-gating; search +
pagination; package-detail rendering incl. delay badge; repository create form
bodies; group priority uniqueness/reorder; proxy upstream password write-only;
token show-once + revoke.

**E2E (Playwright against the Rust `server` serving the built UI + real
Postgres/versitygw via the slice-1 harness):**

1. **Single-origin serving:** load `/`, the SPA boots; deep-link `/repositories/foo`
   loads `index.html` and resolves client-side; `/admin/repositories` (API) is not
   shadowed by the SPA fallback.
2. **Login / session:** paste a valid token → land on Browse; invalid token → stays
   on Login with an error; logout clears and redirects. (When §12.2 is present, an
   OIDC redirect variant.)
3. **Admin gating:** non-admin token cannot reach `/admin/*` (redirected); admin
   token sees management nav.
4. **Create-a-repo flow:** admin creates a **hosted** repo via the UI → it appears
   in the repositories list and its `/v3/{repo}/index.json` advertises
   `PackagePublish` (verified via the API directly).
5. **Push-then-see-package:** `dotnet nuget push` (or a raw `PUT /v3/{repo}/package`
   with a fixture `.nupkg`) → the package appears in **Browse** and in **package
   detail** with the pushed version and dependency groups.
6. **Group + priority:** create a group of two members, set priorities in the
   `PriorityList` editor → package detail / browse reflects highest-priority winner
   for an overlapping id+version.
7. **Proxy delay status:** configure a proxy with a delay; a freshly-discovered
   upstream version shows `DelayBadge` (delayed) in the UI and is absent from
   downloadable browse until the window elapses.
8. **No-CORS prod assertion:** the prod (single-origin) server responds without any
   `Access-Control-Allow-Origin` header on API calls, proving the browser uses the
   same origin (no proxy / no CORS path in prod).

## UX / failure modes

- **Auth expiry:** any `401` mid-session clears credentials and routes to `/login`
  with a "session expired" notice; in-flight mutations surface the failure rather
  than silently dropping. Post-§12.2, cookie expiry behaves identically (the `me`
  query 401s).
- **Large lists / pagination:** browse, repositories, tokens all paginate
  server-side (`skip`/`take`); `keepPreviousData` avoids flicker; search is
  debounced. No client-side load-everything.
- **Error states:** every screen renders an `ErrorState` (with retry) and
  `EmptyState`; mutation errors map API error bodies to inline form messages.
- **Show-once secrets:** token plaintext is rendered once with a copy button and a
  clear warning; never stored in a query cache or re-fetched.
- **No-API-proxy pitfalls:** the SPA fallback **must** be mounted last so it never
  shadows `/admin`, `/v3`, `/auth`; dev must point at the Rust origin (or the
  Vite-proxy form) — a misconfigured dev base URL is the most likely footgun, so
  `config.ts` fails loudly if `VITE_FORGE_API_BASE` is unset in dev. Production
  uses a **relative** base URL so there is structurally no way to introduce a Node
  proxy.
- **Redaction:** proxy upstream credentials are write-only in the UI; the edit form
  shows a "set new password" affordance, never the stored value (matches slice-1
  §5 redaction).

## Open questions / risks

1. **Slice-1 admin DTO shapes.** This plan infers the repository/user/token CRUD
   request/response shapes from §3/§8. They must be reconciled against the real
   slice-1 `server` DTOs at integration time; `src/api/*` types are the single
   place to fix.
2. **Download stats granularity.** Depends on whether slice 1 persists per-version
   counts and/or a time series (Appendix A shows `downloads`). If only aggregate
   exists, `/stats` degrades gracefully.
3. **Login UX before §12.2.** Token-paste is a stopgap; it is acceptable for an
   internal admin tool but should be replaced by OIDC sessions (§12.2) for general
   use. Storing a token in `localStorage` is an accepted risk for the stopgap.
4. **Embed vs. external dir.** Recommend external dir by default; the `web-ui`
   embed feature is opt-in. Confirm the deployment story (container layout) with
   ops before committing to embedding.
5. **SPA vs. SSR.** Recommendation is **SPA mode** to fully honor the
   no-Node-proxy rule. If SEO/first-paint ever matter (they shouldn't for this
   tool), revisit only with a strict rule that SSR data-fetching calls the Rust
   API directly and never re-exposes it — but the simpler, constraint-safe choice
   is SPA.
