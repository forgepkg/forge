# Credential-forwarding authentication backend — Design & Implementation Plan

**Date:** 2026-05-29
**Slice:** §12.3 of the envisia-forge design (NuGet registry)
**Status:** Draft plan (forward-looking; builds on approved Slice 1)

> Builds on Slice 1 crates (`storage`, `db`, `cache`, `core`, `format-nuget`,
> `server`), the `app_user` / `token` tables, the principal-extraction
> middleware (§5), the proxy SSRF guard (§7), and the no-in-memory-only-state /
> scale-out constraint (§2.1, §13). Does **not** restate Slice 1 — see
> `specs/2026-05-29-envisia-forge-nuget-design.md`.

## Goal

Let an operator point envisia-forge at an existing upstream identity provider
(typically a Nexus) and have **end-user logins** validated by forwarding the
supplied username/password to that upstream over HTTP Basic — the
`github.com/schmitch/verdaccio-nexus-auth-proxy` pattern. A user who can log in
to the upstream can log in to forge without an operator pre-creating their
account; a matching `app_user` is auto-provisioned on first success. This is an
**authentication provider for end-user logins**, distinct from a proxy
repository's *own* upstream-fetch credentials (`upstream_username` /
`upstream_password`, already in Slice 1).

## Architecture (2–4 sentences)

Slice 1 has exactly one implicit credential check (local argon2id password,
plus token lookup) baked into the principal-extraction middleware. This slice
extracts that check into a **pluggable, ordered `AuthProvider` chain** owned by
`core`: the middleware resolves a `(username, secret)` pair by walking the
chain until a provider accepts or all reject. `local-password` (Slice 1
behavior, refactored) and a new `upstream-basic` provider are the first two
implementations; an `oidc` provider (§12.2) slots into the same trait. Because
NuGet clients send Basic credentials on *every* request, the `upstream-basic`
provider never forwards on the hot path unconditionally — a **validated-credential
cache** keyed on a salted hash of the password (in the shared `cache` crate,
L1+L2 over Postgres/Redis, never plaintext, never process-memory-authoritative)
absorbs the repeat requests, with bounded TTL and explicit revocation.

## Dependencies

- **Slice 1 crates:** `core` (where the `AuthProvider` trait and chain live;
  this slice introduces them), `db` (data-access for `app_user`, new
  `auth_source` column, new `validated_credential` table fallback when Redis is
  absent), `cache` (L1 moka + optional L2 Redis + invalidation backplane — used
  for the validated-credential cache), `server` (config wiring, principal
  middleware refactor), `storage`/`format-nuget` (unaffected).
- **Slice 1 tables:** `app_user`, `token` (unchanged shape except a new
  `auth_source` / provenance column on `app_user`).
- **Slice 1 patterns reused verbatim:** SSRF guard (§7 — scheme + private-range
  block, DNS re-check at connect, bounded redirects), secret redaction (§5 —
  the configured upstream basic-auth bind credentials, if any, are redacted from
  all API responses and are forward-compatible with §12.5 double-envelope
  encryption), Postgres advisory locks / `SELECT … FOR UPDATE SKIP LOCKED` for
  cross-instance coordination, argon2id (already a dependency).
- **§12.2 OIDC (sibling slice):** shares the `AuthProvider` trait this slice
  defines. See the cross-slice note at the end and the "Open questions" section.

## Tech-stack additions

- **`reqwest`** — already a Slice 1 dependency (proxy upstream client). Reused
  for the upstream-basic request; configure with the same SSRF-aware connector
  as the proxy (custom DNS resolution / connect-time IP check), explicit
  connect + total timeouts, and TLS via the existing rustls/native-tls choice
  Slice 1 made.
- **`argon2`** — already present (password hashing). Reused as the **salted hash
  for the validated-credential cache key** (see cache design — a fast variant /
  HMAC-SHA256 with a server-held pepper is the leading option; decided in
  Phase 3).
- No new crates strictly required. Possible small additions: `hmac` + `sha2`
  (likely already transitively present via `token` hashing) for the cache-key
  derivation.

## 1. Scope

### In scope

- An ordered, configurable `AuthProvider` chain in `core`, replacing the
  hard-coded password/token check in the Slice 1 principal middleware with a
  thin adapter over the chain. Token auth (`X-NuGet-ApiKey` / Basic-as-token)
  stays **ahead of** the password-provider chain and is unchanged.
- A `local-password` provider (refactor of Slice 1's password-basic path; no
  behavior change).
- An `upstream-basic` provider: forward `username:password` to a configured
  upstream over HTTP Basic, interpret a configured success status (default:
  2xx ⇒ accept, 401/403 ⇒ reject), with timeouts, TLS, SSRF guard, and an
  optional required-group/role check parsed from the upstream response.
- **Auto-provisioning:** on first successful upstream login, create a matching
  `app_user` (`auth_source = 'upstream-basic'`, no local password hash,
  `active = true`); subsequent logins reuse it. Admin status is **not** granted
  by this provider unless explicitly mapped (see config).
- **Validated-credential cache:** shared-store (L1+L2) positive **and** negative
  cache keyed on `(provider, username, salted-password-hash)`, bounded TTL,
  revocation hooks, fail-closed on upstream outage. So that the steady state of
  NuGet's per-request Basic auth is a cache hit, not an upstream round-trip.
- Config surface (`auth.providers`, `auth.upstream_basic.*`).
- Unit + e2e tests against a **mock upstream** returning 200/401.

### Explicitly out of scope

- **OIDC (§12.2)** — separate slice. This plan only ensures the trait/chain it
  defines is shaped so OIDC plugs in without rework (see cross-slice note).
- **Fine-grained RBAC (§12.4)** — upstream group/role data is used here only as
  a coarse *allow/deny gate* (optional required-group) and optionally to set
  `is_admin`. Full role mapping to forge privileges is §12.4. We add a
  forward-compatible place to *stash* the raw upstream groups, but do not act on
  them beyond the gate.
- **Secret encryption at rest (§12.5)** — the upstream *bind* credentials (if
  the provider uses a service account to read group info) are stored with the
  same redaction discipline as Slice 1's `upstream_password`, in a dedicated
  redactable column, ready for §12.5 to encrypt. No encryption implemented here.
- **Sessions / cookie login UI** — that's §12.2/§12.6. This slice is purely the
  per-request / token-mint credential validation path.
- **Multiple simultaneous upstream-basic providers** — one configured
  upstream-basic provider in this slice (the chain *type* supports N, but we
  ship one upstream-basic instance). Multi-upstream is a trivial later extension.
- LDAP/SAML/other backends — not in this slice (the chain makes them additive).

## 2. Design

### 2.1 The `AuthProvider` chain

Lives in `core`. The middleware no longer knows *how* a password is checked; it
asks the chain.

```rust
// crates/core/src/auth/provider.rs — illustrative, not final

/// A credential an end user presents for password-style auth.
/// (Token auth is handled before the chain and is not a provider.)
pub struct PasswordCredential<'a> {
    pub username: &'a str,
    pub password: &'a str,
    /// Carried for audit/SSRF-context; never used as a trust signal.
    pub client_ip: std::net::IpAddr,
}

/// Outcome of one provider's attempt.
pub enum AuthOutcome {
    /// Provider authenticated the user. `provisioned` carries the identity
    /// the provider vouches for, so `core` can map/auto-provision an app_user.
    Authenticated(ProvenIdentity),
    /// Provider definitively rejected (e.g. upstream 401). Chain stops here
    /// for this provider but may continue to the next provider.
    Rejected,
    /// Provider can't decide (e.g. this username isn't ours / upstream down +
    /// fail-closed policy). Chain continues to the next provider.
    Skip,
    /// Provider hit an infrastructure error and policy says fail-closed.
    Unavailable,
}

pub struct ProvenIdentity {
    pub username: String,
    pub source: AuthSource,             // Local | UpstreamBasic | Oidc
    pub external_subject: Option<String>,
    pub groups: Vec<String>,            // raw upstream groups/roles (coarse)
    pub suggested_is_admin: bool,       // from admin-group mapping, if any
}

#[async_trait::async_trait]
pub trait AuthProvider: Send + Sync {
    fn id(&self) -> &'static str;       // "local-password" | "upstream-basic" | "oidc"
    fn source(&self) -> AuthSource;
    /// Validate a username/password. MUST be safe to call on the hot path:
    /// providers that do network I/O MUST consult the validated-credential
    /// cache themselves (or be wrapped — see 2.5).
    async fn authenticate(&self, cred: &PasswordCredential<'_>) -> AuthOutcome;
}
```

**Chain semantics** (in `core::auth::Chain`):

1. Iterate providers in configured order.
2. First `Authenticated` wins → `core` maps `ProvenIdentity` to an `app_user`
   (lookup by `(username)`; auto-provision if absent and the provider's
   `auto_provision` is on), updates `last_used_at`, returns the `User`
   principal. Auto-provision and admin-mapping run in `db` inside a transaction.
3. `Rejected` from a provider does **not** stop the chain (so a user could be
   local *or* upstream); a `Rejected` is remembered so that if *every* provider
   returns `Rejected`/`Skip`/`Unavailable` the result is 401 (or 503 if any
   provider was `Unavailable` and policy is fail-closed — configurable, default
   fail-closed → 503 vs 401: we choose **401** to avoid leaking upstream
   health, but log + metric the `Unavailable`; see Security §6).
4. `Skip` → next provider.
5. End of chain with no `Authenticated` → unauthenticated (middleware then
   applies anonymous-mode rules exactly as Slice 1 does).

**Ordering matters and is configurable.** Default `["local-password",
"upstream-basic"]`: a locally-created admin (the bootstrap admin) always works
even if the upstream is down, and we only forward upstream for credentials the
local store didn't accept. Operators who want "upstream is the source of truth"
can set `["upstream-basic", "local-password"]`. The bootstrap admin (§5) is
always a `local-password` identity so it survives upstream outages — documented.

> **Where this hooks into Slice 1:** the Slice 1 middleware step "Basic
> `username:secret` … matched as the user password (if
> `auth.allow_password_basic`)" is replaced by "run the `AuthProvider` chain".
> Token matching (step 1 + Basic-as-token) is unchanged and still runs first.

### 2.2 Data-model changes

Migration `migrations/NNNN_auth_providers.sql`:

- **`app_user`** — add provenance:
  - `auth_source text not null default 'local'` — `'local'` | `'upstream-basic'`
    | (later) `'oidc'`. Backfill existing rows to `'local'`.
  - `external_subject text null` — opaque upstream identifier when the source
    isn't local (for upstream-basic this is usually just the username; kept for
    symmetry with §12.2's `external_identity`).
  - `last_auth_source_at timestamptz null` — last successful auth via a
    non-local source (audit).
  - `password_hash` becomes **nullable** (upstream/oidc users have no local
    password). Local users still require it. Add a check or app-level invariant:
    `auth_source = 'local'` ⇒ `password_hash` not null.
  - Optional `upstream_groups jsonb null` — last-seen raw upstream groups,
    stashed for §12.4. Not authoritative for authz in this slice.

- **`validated_credential`** — the Postgres backing of the validated-credential
  cache, used when Redis (L2) is absent and as the durable source the `cache`
  crate's factory reads/writes (so a cold instance doesn't re-forward):
  - `id bigint pk`,
  - `provider text not null` (`'upstream-basic'`),
  - `username text not null`,
  - `cred_key bytea not null` — the salted password hash (the cache key; see
    2.5). **Never the plaintext.**
  - `outcome text not null` (`'positive'` | `'negative'`),
  - `groups jsonb null` (only for positive; coarse),
  - `expires_at timestamptz not null` (TTL),
  - `created_at timestamptz not null default now()`.
  - Unique `(provider, username, cred_key)`. Index `(expires_at)` for sweeping.
  - A background sweeper (reuse the Slice 1 outbox-worker pattern / a periodic
    tokio job with `DELETE … WHERE expires_at < now()`) purges expired rows.

  > **Why a table and not Redis-only:** §2.1 forbids in-memory-only
  > authoritative state and Redis is *optional*. The authoritative validated
  > result lives in Postgres; `cache` puts L1(moka)+L2(redis) in front. A cold
  > instance with no Redis still avoids re-forwarding by reading this table.
  > (If an operator considers the table itself too sensitive, the
  > `auth.upstream_basic.cache_backend = "memory"` option restricts caching to
  > L1-only with a short TTL — documented trade-off, still scale-out-correct
  > because it's just a perf cache, never authoritative for the *decision*; the
  > decision can always be re-derived by forwarding.)

- **No change** to `token`. Token minting is unaffected: once a user is
  authenticated by *any* provider, they hit the existing admin/token endpoints
  to mint repository tokens. NuGet clients then use tokens (the recommended
  path), which **bypass the chain entirely** — so the per-request-forward
  problem only exists for clients that insist on password Basic.

### 2.3 Config

TOML + `FORGE_*` env overrides (consistent with §8). New keys under `auth`:

```toml
[auth]
# Ordered provider chain. Unknown ids are a startup error.
providers = ["local-password", "upstream-basic"]

[auth.upstream_basic]
enabled = true
# Upstream endpoint hit with the user's Basic credentials. For Nexus this is
# the status/whoami endpoint (verdaccio plugin used /service/rest/v1/status).
url = "https://nexus.internal.example.com/service/rest/v1/status"
# HTTP method (Nexus status is GET).
method = "GET"
# Status codes that mean "credentials valid".
success_status = [200]              # default 2xx
# Status codes that mean "definitively rejected" (-> Rejected, not Unavailable).
reject_status = [401, 403]
connect_timeout_ms = 2000
request_timeout_ms = 5000
# Reuse Slice 1 proxy SSRF policy; allow private only for internal mirrors.
allow_private_upstream = true       # nexus is usually on RFC1918 -> opt-in
# TLS: reuse server TLS config; optionally pin/trust a custom CA bundle.
ca_bundle_path = ""                 # empty -> system roots
# Auto-provision an app_user on first successful login.
auto_provision = true
# Optional coarse gate: only accept if the upstream response shows one of these
# groups/roles. Empty -> any successful auth is accepted.
required_groups = []                # e.g. ["nuget-users"]
# How to read groups from the upstream response (see 2.4). If unset, no group
# data is parsed and required_groups MUST be empty.
groups_jsonpath = ""                # e.g. "$.roles[*]" against a whoami body
# Optionally map an upstream group to forge admin.
admin_group = ""                    # e.g. "nx-admin" -> sets is_admin on provision
# Validated-credential cache.
[auth.upstream_basic.cache]
positive_ttl_secs = 300             # how long a good password is trusted
negative_ttl_secs = 30              # how long a bad password is remembered
backend = "shared"                  # "shared" (postgres+redis) | "memory" (L1 only)
# Server-held pepper for the cache key derivation. Redacted; §12.5-encryptable.
key_pepper = "env:FORGE_AUTH_CACHE_PEPPER"
```

- All secret-ish values (`key_pepper`, any future service-account bind password)
  are **redacted** in every API/config dump exactly like Slice 1's
  `upstream_password`, and stored in dedicated columns/secret slots so §12.5 can
  encrypt them without schema churn.
- Startup validation: unknown provider id → fail to boot; `upstream_basic.url`
  validated through the SSRF guard's scheme check at config time;
  `required_groups` non-empty but `groups_jsonpath` empty → config error.

### 2.4 The `upstream-basic` provider

`crates/core/src/auth/upstream_basic.rs`. Mirrors the verdaccio plugin but
hardened for a multi-instance registry.

Flow of `authenticate(cred)`:

1. **Cache-first** (the whole point — see 2.5): compute `cred_key`, look up the
   validated-credential cache. Positive + unexpired → `Authenticated` (rebuild
   `ProvenIdentity` from cached groups). Negative + unexpired → `Rejected`. Miss
   → continue.
2. **Singleflight per `(username, cred_key)`** so a burst of NuGet requests with
   the same password forwards **once**: `moka try_get_with` for in-process
   coalescing + a **Postgres advisory lock** keyed on a hash of
   `(provider, username, cred_key)` for cross-instance coalescing (the exact
   pattern Slice 1 uses for proxy upstream fetches). The lock holder forwards;
   others wait then read the freshly-written cache row.
3. **Forward:** build a `reqwest` request to `url` with
   `Authorization: Basic base64(username:password)` (verdaccio plugin behavior).
   Use the **SSRF-guarded connector** (resolve DNS, reject loopback/link-local/
   private unless `allow_private_upstream`, re-check at connect, bound
   redirects). Apply `connect_timeout_ms` / `request_timeout_ms`.
4. **Interpret:**
   - status ∈ `success_status` → parse optional groups (`groups_jsonpath`
     against the JSON body, if configured), apply `required_groups` gate
     (if the user lacks a required group → treat as `Rejected`, cache negative),
     compute `suggested_is_admin` from `admin_group`. Write a **positive** cache
     entry (TTL `positive_ttl_secs`, store coarse groups). Return
     `Authenticated`.
   - status ∈ `reject_status` → write **negative** entry (TTL
     `negative_ttl_secs`). Return `Rejected`.
   - other status / network error / timeout → **do not cache**; return
     `Unavailable` (fail-closed; see Security). Never cache an `Unavailable`.
5. The static-user env bypass that the verdaccio plugin had
   (`NEXUS_PROXY_STATIC_USER` / `_PASSWORD`) is **intentionally not ported** —
   forge's equivalent is the `local-password` provider + bootstrap admin, which
   is cleaner and already auditable. (Noted so reviewers don't expect it.)

Auto-provision (in `core` after `Authenticated`, in `db` transaction): upsert
`app_user` by `username`; if new, set `auth_source = 'upstream-basic'`,
`password_hash = NULL`, `active = true`, `is_admin = suggested_is_admin`,
`external_subject = username`; if existing, update `upstream_groups`,
`last_auth_source_at`. **Never** downgrade an existing local admin or flip
`is_admin` off here (admin is operator-managed unless `admin_group` is set; even
then we only *grant*, never revoke, in this slice — revocation semantics are a
§12.4 concern; documented).

### 2.5 Validated-credential cache (security-critical)

**Problem.** NuGet clients send Basic credentials on every request. Forwarding
each one upstream is unacceptable (latency, upstream load, outage amplification).
We cache the *validation decision*, not the credential.

**Cache key.** `cred_key = HMAC-SHA256(pepper, provider || ":" || username || ":" || password)`,
where `pepper` is a server-held secret (`auth.upstream_basic.cache.key_pepper`,
redacted, §12.5-encryptable). Properties:

- **No plaintext password is ever stored** — only `cred_key`. The plaintext
  exists transiently in the request and in the outbound Basic header to the
  configured upstream (unavoidable for a forwarding scheme), never at rest.
- **Pepper (keyed hash), not a bare salt+slow-hash.** A bare hash of the
  password would be offline-bruteforceable if the DB leaked. HMAC with a
  server-held pepper means a DB-only compromise cannot brute-force passwords
  without also stealing the pepper (which lives in env/KMS, not the row). We
  deliberately do **not** use a per-row random salt as the *only* defense,
  because the cache must be *lookup-by-credential* (we don't have the row before
  we have the key), so a per-row salt can't be applied at lookup time — the
  pepper is the right primitive here. (argon2id, the slow hash used for
  `app_user.password_hash`, is *not* suitable as the cache key because we'd have
  to store the salt to recompute and slow-hashing on every NuGet request defeats
  the cache's purpose; the pepper-HMAC gives the leak-resistance without the
  per-request cost.)
- Include `username` in the HMAC input so the same password for two users yields
  distinct keys (no cross-user inference).

**Layering (reuse the `cache` crate).** Lookups go L1(moka) → L2(redis,
optional) → factory. The **factory** is `validated_credential` (Postgres) read,
and on a true miss the factory runs the singleflighted upstream forward (2.4)
and writes Postgres (authoritative) + L2 + L1. This is the same HybridCache
shape Slice 1 already built; we add one cache "namespace". A cold instance
without Redis still reads Postgres and avoids re-forwarding.

**TTL.** `positive_ttl_secs` (default 300s — small enough that a disabled/
password-changed upstream user loses access within minutes, large enough to
absorb a `dotnet restore`'s request fan-out). `negative_ttl_secs` short
(default 30s) to avoid locking out a user who just fixed their password while
still throttling brute-force amplification.

**Revocation.** Three triggers, all via the `cache` crate's invalidation
backplane (the Slice 1 Redis pub/sub drop + Postgres delete):
1. Admin "force re-auth user X" admin-API action → delete all
   `validated_credential` rows for `username` + broadcast L1/L2 invalidation.
2. Setting a user `active = false` or deleting them → same invalidation.
3. TTL expiry (passive). There is no way to *prove* the upstream still trusts a
   credential mid-TTL without forwarding; the TTL bounds that staleness. This is
   the explicit, documented trust window.

**Scale-out.** Authoritative decision in Postgres; L1+optional-L2 in front;
cross-instance forward coalescing via advisory lock; invalidation via backplane.
No instance relies on another's memory. Fully consistent with §2.1.

### 2.6 SSRF guard reuse

The `upstream_basic.url` and any redirect target go through the **same** guard
Slice 1 wrote for proxy `remote_url` (§7): `http`/`https` only; reject
loopback/link-local/private ranges unless `allow_private_upstream`; DNS
re-checked at connect time; bounded redirects, each re-validated. We extract
that guard into a shared helper in `core` (if Slice 1 left it inside the proxy
module) so both the proxy fetch and this provider share one implementation —
flagged as an assumption about Slice 1 internals (see Open questions).

### 2.7 Endpoints

No new public NuGet endpoints. The chain is invoked transparently by the
existing principal middleware for repo + admin requests. **One** new admin-API
action (admin-only, in `server`):

- `POST /admin/users/{username}/reauth` — purge that user's
  validated-credential cache entries + broadcast invalidation (the revocation
  trigger above). Returns 204.

Optionally a read-only `GET /admin/auth/providers` returning the configured,
**redacted** provider chain for operator visibility.

## 3. Phased implementation plan (TDD-ordered)

Each phase: write the test(s) first (red), implement (green), refactor. Concrete
paths assume the Slice 1 layout. Where a Slice 1 internal is assumed, it's
flagged.

### Phase 0 — Migration + provenance (no behavior change)

- **Task:** add `migrations/NNNN_auth_providers.sql`: `app_user.auth_source`,
  `external_subject`, `last_auth_source_at`, `upstream_groups`,
  nullable `password_hash` (+ invariant); create `validated_credential` table
  with unique `(provider, username, cred_key)` and `expires_at` index.
- **Task:** extend `crates/db` data-access: `app_user` upsert-by-username with
  provenance; `validated_credential` get/put/delete-by-username/sweep-expired.
- **Tests** (`crates/db` integration tests against the testcontainers Postgres):
  migration applies + backfills existing users to `'local'`; `password_hash`
  nullable accepted for upstream users, rejected for local; `validated_credential`
  unique constraint; sweep deletes only expired.

### Phase 1 — `AuthProvider` trait + chain in `core`

- **Task:** `crates/core/src/auth/provider.rs` — `AuthProvider`, `AuthOutcome`,
  `ProvenIdentity`, `AuthSource`, `PasswordCredential`.
- **Task:** `crates/core/src/auth/chain.rs` — `Chain::authenticate` ordering
  semantics (first `Authenticated` wins; `Skip` continues; `Rejected`/
  `Unavailable` accounting; auto-provision/map via a `db` callback).
- **Task:** `crates/core/src/auth/mod.rs` — module wiring.
- **Tests** (`core` unit tests, with **fake in-memory providers** implementing
  the trait — no network): ordering (local-before-upstream vs reversed); first
  `Authenticated` short-circuits provisioning of later providers; all-`Skip` →
  unauthenticated; a provider `Authenticated` triggers the auto-provision
  callback exactly once; `Unavailable` handling per policy.

### Phase 2 — Refactor Slice 1 password path into `local-password` provider

- **Task:** `crates/core/src/auth/local_password.rs` — implement `AuthProvider`
  over the existing argon2id verify against `app_user.password_hash`
  (`auth_source = 'local'` only; others → `Skip`).
- **Task:** `crates/server` principal middleware — replace the inline
  password-basic check (Slice 1 §5 step 2) with a call into `core::auth::Chain`.
  Token path unchanged and still first. **No behavior change** when the chain is
  just `["local-password"]`.
- **Tests:** the **existing** Slice 1 principal-extraction tests must still pass
  unchanged (regression guard). Add: chain configured with only local-password
  reproduces Slice 1 password-basic on/off behavior and invalid-creds→401.

### Phase 3 — Validated-credential cache

- **Task:** `crates/core/src/auth/cred_cache.rs` — `cred_key` derivation
  (HMAC-SHA256 with pepper), and a `ValidatedCredentialCache` that uses the
  `cache` crate (L1+L2) with the Postgres `validated_credential` factory + the
  invalidation backplane. Positive/negative entries, TTLs, revoke-by-username.
- **Tests** (`core` unit + `db` integration): `cred_key` is stable, peppered,
  per-user-distinct, and the plaintext never appears in the stored bytes
  (assert the row's `cred_key != password` and is HMAC-length); positive hit
  returns without invoking the (mocked) factory; negative hit short-circuits;
  TTL expiry forces a factory call; revoke-by-username deletes rows + fires
  invalidation (mock backplane). **Explicit test: store a credential, dump the
  whole `validated_credential` table, assert no plaintext password substring
  anywhere.**

### Phase 4 — `upstream-basic` provider

- **Task:** `crates/core/src/auth/upstream_basic.rs` — the provider per 2.4,
  wired to `ValidatedCredentialCache` (cache-first), the SSRF-guarded `reqwest`
  client, singleflight (moka + advisory lock), status interpretation, optional
  `groups_jsonpath` + `required_groups` gate + `admin_group` mapping.
- **Task:** extract/locate the SSRF guard helper in `core` (Phase 4a if Slice 1
  buried it in the proxy module).
- **Tests** (`core` integration with an **in-process mock HTTP upstream**, e.g. a
  tiny axum/`wiremock` server returning 200/401/timeout):
  - 200 → `Authenticated`, positive cached;
  - 401 → `Rejected`, negative cached;
  - second identical request → **no second upstream call** (assert mock hit
    count == 1) served from cache;
  - TTL expiry → second upstream call happens;
  - timeout / 5xx → `Unavailable`, **nothing cached** (assert next call
    re-forwards);
  - `required_groups` unmet → `Rejected` despite 200;
  - `admin_group` present in response → `suggested_is_admin = true`;
  - SSRF: `url` resolving to a private address with `allow_private_upstream =
    false` → provider errors at config/connect (reuse Slice 1 SSRF test
    helpers).

   the upstream-valid credential via Basic on an admin endpoint → 200; an
   `app_user` now exists with `auth_source='upstream-basic'`, null
   `password_hash`.
2. **401 rejection:** wrong password → forge returns 401; no `app_user` created;

3. **Cache hit avoids second upstream call:** two back-to-back authenticated

   request (assert via the mock's hit counter).
4. **Cache TTL expiry:** set `positive_ttl_secs` tiny; after expiry a third
   request triggers a second upstream call.
5. **Provider ordering:** with `["local-password","upstream-basic"]`, a user who
   exists locally is authenticated **without** any upstream call (mock hit count
   0); reverse the order and the upstream is consulted first.
6. **Plaintext never stored:** after a successful + a failed login, dump
   `validated_credential` and `app_user`; assert neither contains the plaintext
   password as a substring (bytea and text columns).
7. **Upstream outage → fail closed:** mock in "down" mode → request that isn't a
   cache hit returns 401 (auth fails); a *cached* positive within TTL still

8. **Revocation:** authenticate (positive cached) → admin `POST
   /admin/users/{u}/reauth` → next request re-forwards (mock hit count

## 5. Security & failure modes

- **Password-hash-as-cache-key safety.** Key = HMAC-SHA256(pepper, provider |
  username | password). DB-only compromise can't brute-force passwords without
  the pepper (env/KMS, §12.5-encryptable). No plaintext at rest (tested,
  Testing #6). Per-user-distinct keys prevent cross-user inference. The pepper
  must be high-entropy and rotated via §12.5 machinery; rotating it invalidates
  the whole cache (acceptable — it just causes re-forwards).
- **Fail closed on upstream outage.** Non-cached request during outage → 401
  (auth denied), never a default-allow. Outages are **never** negatively cached
  (so a flapping upstream doesn't lock everyone out past the blip) and never
  positively cached. Cached positives within TTL still work, bounding blast
  radius to the TTL window. The bootstrap/local admin always works (local
  provider, no upstream) so operators aren't locked out — this is why
  `local-password` should generally precede `upstream-basic`.
- **Credential-cache poisoning.** Only the singleflight winner (advisory-lock
  holder) writes a cache entry, and only from a *real* upstream
  success/reject — `Unavailable` writes nothing. The `cred_key` is server-keyed,
  so a client can't craft a key for another user. Cache writes go through `db`
  with the unique constraint; no client-controllable key path.
- **Timing.** Cache hits are fast; upstream forwards are slow — an attacker
  could distinguish "cached" vs "forwarded" and infer recent activity for a
  username, but not validity (both 200-cached and 401-cached are fast). We do
  **not** add artificial constant-time delays (cost/benefit poor for a registry
  behind a network), but we keep the negative-cache TTL short and rely on
  upstream rate-limiting + forge-side per-IP throttling (a §12.4-adjacent
  follow-up; noted). Token comparison and password verify remain constant-time
  as in Slice 1.
- **SSRF.** `upstream_basic.url` + redirects go through the Slice 1 guard;
  private ranges blocked unless `allow_private_upstream` (needed for typical
  internal Nexus, hence opt-in with a documented risk note). DNS re-checked at
  connect.
- **Credential exposure in transit.** The user's plaintext is sent to the
  configured upstream over the Basic header — *require HTTPS* for the upstream
  url in non-dev (warn loudly if `http://`). The forge↔client leg already
  expects TLS-terminating reverse proxy (Slice 1 posture). Outbound Basic header
  and the pepper are redacted from logs/metrics/error bodies (Slice 1 redaction
  discipline).
- **Privilege escalation via groups.** `admin_group` only *grants*, never
  revokes, in this slice; an existing local admin is never downgraded by an
  upstream login. Full role mapping is §12.4.

## 6. Open questions / risks

1. **Slice 1 SSRF guard location.** Plan assumes the guard is reusable from
   `core`; if Slice 1 left it inside the proxy module, Phase 4a extracts it.
   *Assumption flagged.*
2. **Slice 1 cache-crate API shape.** Plan assumes `cache` exposes a generic
   namespaced get-or-factory + invalidate that we can add an "auth" namespace to.
   If its API is hard-coded to proxy metadata, a small generalization is needed.
   *Assumption flagged.*
3. **Principal middleware seam.** Plan assumes the Slice 1 middleware cleanly
   isolates the password-basic step so it can be swapped for the chain without
   touching the token path. If they're entangled, Phase 2 is slightly larger.
4. **`groups_jsonpath` dependency.** Parsing groups from an arbitrary upstream
   body may want a JSONPath crate. Risk: scope creep. Mitigation: ship with the
   gate **disabled by default** (empty `groups_jsonpath`), so v1 only needs
   status-code interpretation (matches the verdaccio plugin exactly); add
   JSONPath parsing only if `required_groups`/`admin_group` are configured.
5. **Default fail policy nuance:** returning 401 (not 503) on `Unavailable`
   hides upstream health but may confuse operators debugging an outage. We log +
   metric `Unavailable` distinctly. Revisit if operators want a `strict_503`
   toggle.
6. **Username collision across sources.** If a local user and an upstream user
   share a username, ordering decides who wins and auto-provision must not
   clobber the local row. Plan: never overwrite a `'local'` row's `auth_source`
   or `password_hash` during upstream provision; document that usernames are a
   single namespace.
7. **Per-IP throttling** for repeated bad-password Basic attempts is desirable
   (brute-force amplification through the negative cache is limited but not
   zero). Deferred to a small follow-up / §12.4; noted.
