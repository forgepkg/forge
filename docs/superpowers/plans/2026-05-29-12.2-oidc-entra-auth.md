# OIDC / Microsoft Entra authentication — Design & Implementation Plan

**Date:** 2026-05-29
**Slice:** §12.2 of the `envisia-forge` design (depends on the approved Slice 1 spec,
`2026-05-29-envisia-forge-nuget-design.md`)
**Status:** Draft — forward-looking plan

## Goal

Add interactive **OpenID Connect login** (authorization-code flow with PKCE),
primarily against **Microsoft Entra ID**, so humans can sign in to the (future)
admin/browse UI with their corporate identity. Logged-in users get a
**server-side session** (cookie → session row in a shared store) and can **mint
repository `token`s** through the existing slice-1 token model for use by NuGet
clients/CI. OIDC identities map to `app_user` rows via a new `external_identity`
table, with optional auto-provisioning and claim/group-driven `is_admin`
assignment. This slice does **not** change how NuGet protocol endpoints
authenticate (those stay token/basic per slice 1); it only adds a browser login
surface and the plumbing behind it.

## Architecture (overview)

OIDC lives in `core` as an `oidc` module plus an `auth-provider`-shaped seam,
wired into `server` as a small set of `/auth/...` routes and a session-cookie
middleware that runs ahead of (and feeds into) the slice-1 principal-extraction
middleware. All ephemeral auth-code-flow state (`state`, `nonce`, PKCE verifier,
post-login redirect) and all login sessions are written to **Postgres** (with an
optional Redis L2 via the `cache` crate), never to process memory, so any
instance can complete a callback that a different instance started — satisfying
the slice-1 no-in-memory-only-state / horizontal-scale-out constraint. JWKS and
OIDC discovery documents are fetched once and cached through the existing
`cache` crate (TTL + cross-node invalidation), with rotation handled by
kid-miss-triggered refetch.

## Dependencies

- **Slice 1 must be merged.** This slice builds directly on:
  - Crates `core`, `db`, `cache`, `server` (we add modules, not new crates).
  - Tables `app_user` (`id`, `username`, `password_hash`, `is_admin`, `active`,
    …) and `token` (`id`, `user_id`, `name`, `token_hash`, `expires_at`,
    `revoked_at`, …). We **reuse** the slice-1 token-minting path; we do not
    redefine the token model.
  - The slice-1 **principal-extraction axum middleware** and the
    `User` / `Anonymous` principal types, plus the authz seam
    (`can_read` / admin checks). We extend the principal source to include
    "session cookie → `User`" *in addition to* token/basic; the existing token
    and basic branches are unchanged. **(Assumption: the slice-1 middleware
    exposes a place to add an additional principal source and a `Principal`/
    `User` type we can construct from a session row. Flagged.)**
  - The slice-1 **config loader** (`FORGE_*` env + TOML) and bootstrap-admin
    machinery (`auth.bootstrap_admin`); OIDC config slots into the existing
    `auth` / new `oidc` config sections.
  - The slice-1 `cache` crate (L1 moka + optional Redis L2 + invalidation
    backplane) for discovery/JWKS caching.
  - The slice-1 migrations runner and `sqlx` compile-time-checked-query
    conventions.
- **Optional Redis** stays optional: sessions and flow-state are authoritative
  in **Postgres**; Redis is only an L2/accelerator, exactly as in slice 1.

## Tech-stack additions (recommended Rust crates)

- **`openidconnect`** (built on **`oauth2`**) — the core dependency. It models
  OIDC discovery, the authorization-code + PKCE flow, ID-token validation
  (issuer, audience, `azp`, `nonce`, signature, expiry/`nbf`), and JWKS. Entra
  is a standard OIDC provider, so this works against it directly. We use it in
  its **lower-level / explicit mode**: we drive each step ourselves
  (build auth URL, exchange code, validate ID token) so we control where
  `state`/`nonce`/PKCE-verifier are persisted (Postgres, not memory). Justify:
  hand-rolling OIDC signature/claim validation is a security footgun; this crate
  is the de-facto Rust choice and is `RustCrypto`-backed.
- **`reqwest`** — already a slice-1 dependency (proxy upstream client). Reused as
  the HTTP client for discovery/JWKS/token-endpoint calls (configure the
  `openidconnect` async HTTP client over `reqwest`). The slice-1 **SSRF/timeout
  posture should apply to the OIDC HTTP client too** for the token endpoint and
  JWKS URI (see Security §6).
- **`jsonwebtoken`** — *not* added directly; `openidconnect` handles JWT/JWKS.
  Listed only to record the decision not to duplicate JWT logic.
- **`rand`** (CSPRNG) — already transitively present (slice-1 token secrets use a
  256-bit CSPRNG). Reused to generate session IDs and the opaque cookie value.
- **`cookie`** / axum's typed cookie support — for setting/clearing the session
  cookie with `Secure; HttpOnly; SameSite=Lax; Path=/`. If axum-extra's
  `cookie` feature is already pulled, use it; otherwise add `axum-extra` with the
  `cookie` feature. No signed/encrypted cookie jar is needed: the cookie carries
  only an **opaque random session id**; all authority is the Postgres session
  row (so cookie tampering is meaningless — an unknown id is just "no session").
- **`time`** / `chrono` — whichever slice 1 standardized on for `timestamptz`
  mapping; reuse it. (Plan assumes the slice-1 choice; do not introduce a second
  time crate.)

No new *crate* (workspace member) is created; all code lands in existing crates.

## 2. Scope

### In scope
- OIDC discovery + JWKS fetch/cache/rotation (Entra-first, but generic OIDC).
- `GET /auth/oidc/login` (start flow) and `GET /auth/oidc/callback` (complete
  flow), authorization-code + PKCE.
- `external_identity` table mapping `(issuer, subject) → app_user`.
- Claim → `app_user` mapping; auto-provision option; `is_admin` from
  claims/groups; interplay with the slice-1 bootstrap admin.
- `session` table + opaque session cookie (secure/httponly/samesite, rotation on
  privilege change, idle + absolute expiry, server-side revocation).
- A session-cookie principal source feeding the slice-1 authz seam.
- `POST /auth/logout` and session revocation.
- `GET /auth/me` (who-am-I for the UI) and an authenticated **token-minting**
  endpoint that reuses the slice-1 token creation path so a logged-in user can
  create repository tokens.
- CSRF defense for state-changing same-site form posts (logout, token mint).
- Multi-instance correctness for the auth-code flow (flow-state + sessions in the
  shared store).
- Unit + e2e tests, including a **mock OIDC provider** and a **cross-instance
  callback** scenario.

### Explicitly out of scope
- The actual frontend UI (§12.6) — this slice ships the HTTP API the UI will
  call, plus minimal redirects; no React.
- The credential-forwarding auth provider / pluggable provider **chain** (§12.3).
  We add OIDC as *an* authentication path and shape its entry point so §12.3 can
  generalize it into a provider chain, but we do **not** build the chain
  abstraction or ordering here (see Open questions — overlap noted).
- Fine-grained RBAC (§12.4): `is_admin` remains the only role, exactly as slice
  1. We only decide *how OIDC sets that boolean*.
- Secret encryption at rest (§12.5): the OIDC `client_secret` is stored like
  slice-1 proxy upstream secrets (config/env, redacted from APIs); encrypting it
  is §12.5's job.
- Front-channel / back-channel **logout initiated by the IdP** (OIDC
  `end_session_endpoint` RP-initiated logout is included as an optional redirect;
  IdP-pushed logout tokens are deferred).
- Refresh tokens / long-lived IdP sessions: we do **not** persist OIDC refresh
  tokens. The forge session lifetime is independent of the IdP token lifetime
  (re-login on session expiry). (See Open questions.)
- Multiple simultaneous OIDC providers: slice supports **one** configured OIDC
  provider (issuer). The schema (`external_identity.issuer`) is multi-provider
  ready; wiring multiple is deferred.

## 3. Design

### 3.1 Data-model changes (Postgres)

Two new tables. Conventions match slice 1 (`bigint` identity PKs, `timestamptz`).

**`external_identity`** — maps an IdP identity to an `app_user`.

```sql
CREATE TABLE external_identity (
    id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id         bigint NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
    issuer          text   NOT NULL,            -- OIDC `iss` (exact match)
    subject         text   NOT NULL,            -- OIDC `sub` (stable per-issuer)
    -- denormalized last-seen claims, for display/debugging only (not authority):
    preferred_username text,
    email           text,
    display_name    text,
    last_login_at   timestamptz,
    created_at      timestamptz NOT NULL DEFAULT now(),
    updated_at      timestamptz NOT NULL DEFAULT now(),
    UNIQUE (issuer, subject)
);
CREATE INDEX external_identity_user_id_idx ON external_identity (user_id);
```

- `(issuer, subject)` is the join key (never email — emails are reassignable;
  `sub` is the stable, issuer-scoped identifier Entra guarantees).
- One `app_user` may have several `external_identity` rows (future multi-IdP);
  unique `(issuer, subject)` prevents duplicate links.

**`session`** — server-side login sessions (the authority; cookie is just a
pointer).

```sql
CREATE TABLE session (
    id              text PRIMARY KEY,            -- 256-bit CSPRNG, base64url; the cookie value
    user_id         bigint NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
    external_identity_id bigint REFERENCES external_identity(id) ON DELETE SET NULL,
    created_at      timestamptz NOT NULL DEFAULT now(),
    last_seen_at    timestamptz NOT NULL DEFAULT now(),  -- idle-timeout clock
    absolute_expiry timestamptz NOT NULL,                -- hard cap regardless of activity
    idle_expiry     timestamptz NOT NULL,                -- last_seen_at + idle_ttl, refreshed on use
    revoked_at      timestamptz,
    -- bound context to detect cookie theft / pinning (optional, see §6):
    user_agent_hash text,
    csrf_secret     text NOT NULL                -- per-session secret for double-submit CSRF
);
CREATE INDEX session_user_id_idx ON session (user_id);
CREATE INDEX session_idle_expiry_idx ON session (idle_expiry);
```

Note: storing the **raw** session id as PK is acceptable because the id is a
high-entropy opaque secret and the row carries no other authentication factor;
to harden against DB-read disclosure we **hash** it (`session.id =
sha256(cookie_value)`, mirroring slice-1 `token_hash`). **Decision: hash it** —
the cookie carries the plaintext 256-bit value, the PK stores its sha256, looked
up in constant time, consistent with the slice-1 token pattern. (Adjust the
column comment accordingly.)

**`oidc_flow`** — ephemeral auth-code-flow state, shared across instances. This
is the crux of multi-instance correctness.

```sql
CREATE TABLE oidc_flow (
    state           text PRIMARY KEY,            -- CSPRNG; also the OAuth `state` param
    nonce           text NOT NULL,               -- CSPRNG; checked against ID-token `nonce`
    pkce_verifier   text NOT NULL,               -- PKCE code_verifier (S256)
    redirect_to     text NOT NULL,               -- validated post-login relative path
    created_at      timestamptz NOT NULL DEFAULT now(),
    expires_at      timestamptz NOT NULL         -- short, e.g. now()+10min
);
CREATE INDEX oidc_flow_expires_at_idx ON oidc_flow (expires_at);
```

- Rows are **single-use**: the callback `DELETE … RETURNING` the row (atomic
  consume) — a replayed `state` finds nothing → reject. This both enforces
  one-time use and is naturally race-safe across instances (only one `DELETE`
  returns the row).
- Like `session`, the `state`/`nonce`/`pkce_verifier` could be sha256-stored, but
  the verifier must be sent back to the IdP verbatim, so `oidc_flow` stores them
  as-is; rows are short-lived and deleted on use. (`state` is also the lookup key
  the IdP echoes, so it cannot be hashed.)

A periodic cleanup job (or `DELETE WHERE expires_at < now()` opportunistically on
each callback) reaps expired `oidc_flow` and `session` rows. Reuse the slice-1
background-worker pattern (`SELECT … FOR UPDATE SKIP LOCKED` not needed for pure
`DELETE`; a simple periodic `DELETE` on any instance suffices).

  `external_identity` upsert/lookup by `(issuer, subject)`,

  `sqlx` queries per slice-1 convention.
- **`crates/server/src/routes/auth.rs`** (new) — the `/auth/...` axum router,
  mounted by `server` under `/auth`.
- **`crates/server/src/middleware/session.rs`** (new) — cookie → session
  middleware feeding the principal source; runs before the slice-1 principal
  middleware (or is composed into it — see Assumption in Dependencies).
- **`migrations/NNNN_oidc_auth.sql`** — the three tables above.

### 3.3 Endpoints

All under `/auth`. These are **UI/browser** endpoints; NuGet protocol routes are
unchanged.

| Method | Path | Request | Response |
|---|---|---|---|
| `GET` | `/auth/oidc/login` | optional `?redirect_to=<relative-path>` | 302 → IdP authorize URL; inserts an `oidc_flow` row (state/nonce/PKCE). No cookie set yet (state lives in DB, keyed by `state` param). |
| `GET` | `/auth/oidc/callback` | `?code=&state=` (or `?error=&error_description=&state=`) | On success: consume `oidc_flow`, validate, map user, create `session`, **set session cookie**, 302 → `redirect_to`. On any failure: 400/401, no cookie, generic error. |
| `POST` | `/auth/logout` | session cookie + CSRF token | Revoke session (`revoked_at`), clear cookie (`Max-Age=0`), optional 302 → IdP `end_session_endpoint`. 204/302. |
| `GET` | `/auth/me` | session cookie | `200 {{ user_id, username, is_admin, display_name, email }}` or `401`. For the UI to render auth state. |
| `POST` | `/auth/tokens` | session cookie + CSRF token; body `{{ name, expires_at? }}` | Reuses slice-1 token minting for `session.user_id`. `201 {{ id, name, token (plaintext, shown once), expires_at }}`. |
| `GET` | `/auth/tokens` | session cookie | `200 [{{ id, name, expires_at, last_used_at, created_at }}]` (no secret). |
| `DELETE` | `/auth/tokens/{{id}}` | session cookie + CSRF token | Revoke a token owned by `session.user_id`. `204`/`404`. |

Notes:
- `/auth/oidc/login` deliberately does **not** set a pre-flight cookie. Because
  the `state` parameter is the lookup key into `oidc_flow` (shared store), the
  callback needs **no** instance affinity and **no** cookie to correlate — the
  IdP echoes `state`, we consume the matching DB row. This is what makes a
  cross-instance callback correct (see §3.3.1). The `nonce`+PKCE binding is what
  protects against the cookieless-correlation weakness (CSRF on the callback) —
  see §6.
- The token endpoints live under `/auth` (session-authenticated) deliberately:
  NuGet clients use `X-NuGet-ApiKey`; humans mint those keys here. They are thin
  wrappers over the slice-1 token service, scoped to the session's user.

#### 3.3.1 Multi-instance correctness for state / nonce / PKCE

Concretely, with instances **A** and **B** behind a load balancer:

1. Browser hits `/auth/oidc/login` on **A**. A generates `state`, `nonce`,
   `code_verifier`; computes `code_challenge = S256(code_verifier)`; inserts
   `oidc_flow{{state, nonce, pkce_verifier, redirect_to, expires_at}}` into
   **Postgres**; 302s to Entra with `state` + `code_challenge` + `nonce`.
   **Nothing is held in A's memory.**
2. Entra authenticates the user and redirects the browser to
   `/auth/oidc/callback?code=…&state=…`. The LB may route this to **B**.
3. **B** runs `DELETE FROM oidc_flow WHERE state = $1 AND expires_at > now()
   RETURNING nonce, pkce_verifier, redirect_to`. If no row → reject (unknown,
   expired, or replayed state). B now has the verifier + expected nonce *without
   ever having seen step 1*.
4. B exchanges `code` + `pkce_verifier` at the token endpoint, validates the ID
   token signature against the **cached JWKS** (shared via `cache` crate; B
   fetches+caches if cold), checks `iss`/`aud`/`exp`/`nbf`/`azp` and that the
   token's `nonce` equals the row's `nonce`.
5. B maps claims → `app_user`, inserts a `session` row in Postgres, sets the
   cookie, 302 → `redirect_to`.

Because every piece of authoritative flow state is in Postgres (optionally
fronted by Redis L2), **any** instance completes **any** callback. The atomic
`DELETE … RETURNING` guarantees single-use even under concurrent duplicate
callbacks. This is the explicit answer to the slice-1 "no in-memory-only state"
constraint for auth.

### 3.4 JWKS & discovery caching via the `cache` crate

- **Discovery** (`{{issuer}}/.well-known/openid-configuration`): fetched on first
  use, stored in the `cache` crate under key `oidc:discovery:{{issuer}}` with a
  long TTL (e.g. 24h). Holds authorize/token/jwks/end_session endpoints. Entra's
  discovery is stable; TTL refetch is fine.
- **JWKS** (`jwks_uri` from discovery): cached under `oidc:jwks:{{issuer}}` with a
  moderate TTL (e.g. 1h). The L1 (moka) + optional Redis L2 + invalidation
  backplane from slice 1 are reused verbatim — so a cold instance rebuilds the
  JWKS from the IdP, and an instance that refetches on rotation can broadcast an
  invalidation so peers drop stale keys.
- **Rotation handling (kid-miss refetch):** ID-token validation looks up the
  signing key by `kid`. On a **kid miss** (Entra rolled keys before TTL expiry),
  force a JWKS refetch (bypassing L1/L2, then repopulating + broadcasting
  invalidation) and retry validation **once**. This is the standard robust
  pattern: TTL handles the common case, kid-miss handles early rotation. Bound
  the refetch with the slice-1 **Postgres advisory lock** singleflight so a
  rotation storm doesn't have every instance hammer the JWKS endpoint
  simultaneously (reuse the slice-1 proxy-fetch singleflight mechanism).
- **Clock skew:** allow a small leeway (e.g. 60s) on `exp`/`nbf`/`iat` validation
  (configurable `oidc.clock_skew_seconds`).

### 3.5 OIDC config

New `oidc` config section (TOML + `FORGE_OIDC_*` env, per slice-1 loader). Absent
section ⇒ OIDC disabled, `/auth/oidc/*` returns 404, login UI hidden.

```toml
[oidc]
enabled        = true
issuer         = "https://login.microsoftonline.com/<tenant-id>/v2.0"
client_id      = "..."
client_secret  = "..."                 # redacted from all API responses (like slice-1 upstream_password)
redirect_url   = "https://forge.example.com/auth/oidc/callback"
scopes         = ["openid", "profile", "email"]   # + optional groups scope
clock_skew_seconds = 60

# claim → user mapping
username_claim     = "preferred_username"  # fallback chain: preferred_username → email → sub
email_claim        = "email"
display_name_claim = "name"

# provisioning
auto_provision     = true               # create app_user on first successful login
# admin assignment (see §3.6)
admin_groups       = ["forge-admins"]   # group object-ids or names from `groups`/`roles` claim
admin_claim        = "roles"            # or "groups"; claim whose values are matched against admin_groups
```

`client_secret` is read from env/file and **redacted** from any admin API that
echoes config, mirroring the slice-1 proxy `upstream_password` treatment.
Encrypting it at rest is §12.5.

### 3.6 Claim → user + admin mapping

On a validated callback:

1. **Identity resolution.** Look up `external_identity` by
   `(iss, sub)`. The ID token's `iss` must equal the configured `issuer` (Entra
   v2 issuer includes the tenant) and `aud` must equal `client_id`.
2. **Existing link** → load that `app_user`. Update denormalized
   `preferred_username/email/display_name`, `last_login_at`. Re-evaluate
   `is_admin` from current claims (so admin grant/revoke in the IdP takes effect
   on next login).
3. **No link:**
   - If a matching `app_user` exists *by username* (e.g. a bootstrap admin or a
     pre-created local user whose `username` equals the resolved username claim),
     **link** it: insert an `external_identity` pointing at that user. This is the
     **admin-bootstrap interplay**: the slice-1 bootstrap admin (a local-password
     user) can be claimed by the matching OIDC identity on first OIDC login, so
     the operator's Entra account becomes the admin without a second account.
     (Guard with `oidc.link_existing_by_username`, default `true`; document the
     risk that an IdP-controlled username claim could hijack a local account — so
     `username_claim` should be a verified, non-reassignable claim. For Entra,
     prefer `oid`/`sub`-derived or a verified email; document that
     `preferred_username` is *not* guaranteed unique/stable and recommend
     `link_existing_by_username = false` in untrusted-IdP setups.)
   - Else if `auto_provision = true`: create a new `app_user`
     (`username` = resolved username claim, unique-suffixed on collision,
     `password_hash` = a sentinel "no-password" marker so password-basic can't be
     used for it, `active = true`), then link.
   - Else (`auto_provision = false`, no match): reject with 403 ("user not
     provisioned"). Operator must pre-create the `app_user`.
4. **Admin assignment.** Compute `is_admin = any(values of `admin_claim` ∩
   `admin_groups`)`. For Entra: app roles arrive in the `roles` claim; security
   groups arrive in the `groups` claim (or, when the group set is large, a
   "groups overage" `_claim_names`/`_claim_sources` pointer to Graph — slice-1
   scope: document the overage limitation and recommend **app roles** (`roles`)
   over raw `groups` to avoid the Graph callout; supporting overage is deferred).
   - If `admin_groups` is empty/unset, OIDC never grants admin (admins stay
     locally managed) — safe default.
   - `is_admin` is **recomputed every login** and written to `app_user.is_admin`.
     A user removed from the admin group loses admin on next login; existing
     sessions are not retroactively downgraded mid-session (documented; a future
     RBAC slice §12.4 can do live re-evaluation).

The result is always an `app_user` row; downstream authz uses the unchanged
slice-1 `is_admin` check.

### 3.7 Session lifecycle & cookie semantics

- **Cookie:** name `forge_session`; value = the 256-bit base64url session secret
  (the DB stores its sha256). Attributes: `Secure; HttpOnly; SameSite=Lax;
  Path=/`. `SameSite=Lax` (not `Strict`) so the post-IdP-redirect top-level
  navigation carries the cookie; combined with `oidc_flow` state/nonce this is
  safe. No `Domain` (host-only). Set only over HTTPS in production
  (`server.public_base_url` scheme drives `Secure`).
- **Expiry:** `idle_expiry = last_seen_at + oidc.session_idle_ttl` (e.g. 8h) and
  `absolute_expiry = created_at + oidc.session_absolute_ttl` (e.g. 7d). A session
  is valid iff `revoked_at IS NULL AND now() < idle_expiry AND now() <
  absolute_expiry`. On each authenticated request, **touch** `last_seen_at`/
  `idle_expiry` (best-effort, throttled to avoid a write per request — e.g. only
  if `last_seen_at` is older than 60s, like slice-1 `token.last_used_at`).
- **Rotation:** issue a **new** session id (and delete/revoke the old) right
  after login completes and on any privilege change, to prevent session fixation.
  (Login creates a fresh row, so fixation via a pre-seeded cookie is impossible —
  but we still rotate on privilege elevation.)
- **Revocation / logout:** `POST /auth/logout` sets `revoked_at = now()`, clears
  the cookie. Admin API may revoke any session (`DELETE` by user). Because the
  session row is the authority, revocation is instant cluster-wide (next request
  on any instance re-reads the row). If Redis L2 caches sessions, broadcast an
  invalidation on revoke (reuse `cache` backplane); without Redis, keep the
  session L1 TTL short (seconds) so staleness is bounded — same correctness story
  as slice-1 caches.

### 3.8 CSRF

- The OIDC **callback** is protected by the `state`+`nonce`+PKCE triple
  (`oidc_flow` single-use consume), which is itself the CSRF defense for the login
  flow.
- For **authenticated state-changing endpoints** (`/auth/logout`,
  `POST /auth/tokens`, `DELETE /auth/tokens/{{id}}`): defense in depth =
  `SameSite=Lax` cookie **plus** a **double-submit** token. `/auth/me` returns the
  session's `csrf_secret`; the UI echoes it in an `X-CSRF-Token` header on
  mutating requests; the server compares (constant-time) against the session
  row's `csrf_secret`. This survives multi-instance because the secret lives in
  the session row. (Pure-API token-based NuGet endpoints are not cookie-auth and
  need no CSRF.)

## 4. Phased implementation plan (TDD-ordered)

### Unit tests (per phase above)

### Mock OIDC provider (e2e harness)
Run an **in-process OIDC provider** inside the slice-1 `tests/` harness
alongside the testcontainers Postgres + versitygw + the in-process forge
server(s):

- Implement a tiny axum app that serves `/.well-known/openid-configuration`,
  `/authorize` (immediately 302s back to the forge `redirect_url` with a
  canned `code` + the echoed `state`, simulating an already-authenticated
  user — no real login UI), `/token` (returns a signed ID token + access
  token), and `/jwks` (the public key). Sign ID tokens with an RSA key the
  mock holds; the `kid` is published in `/jwks`. This gives full control over
  claims, `nonce`, `kid` rotation, expiry, and error responses.
- Option B (if we prefer an external image): a Keycloak testcontainer can be
  added gated on availability, but the in-process mock is faster, hermetic, and
  lets us inject malformed tokens — make it the default; Keycloak is optional.

### E2E scenarios
1. **Callback success:** login → mock authorize → callback → session cookie set →
   `/auth/me` returns the mapped user; `is_admin` reflects the mock's group/role
   claim.
2. **State mismatch / replay:** callback with an unknown `state` → 401/400;
   replaying a once-used `state` → rejected (row already consumed).
3. **Nonce mismatch:** mock issues an ID token whose `nonce` ≠ the flow's nonce →
   rejected.
4. **Cross-instance callback (the headline scale-out test):** run **two** forge
   instances (A, B) against the same Postgres (+ optional Redis), as the slice-1
   scale-out test does. Start login on **A** (writes `oidc_flow`), point the mock
   to redirect the callback to **B**. Assert B completes the flow, creates the
   session, and `/auth/me` on **either** instance recognizes the session — proving
   no in-memory-only flow/session state.
5. **Auto-provision vs. reject:** first login with `auto_provision=true` creates
   an `app_user`; with `auto_provision=false` and no pre-created user → 403; with
   a pre-created matching local user (bootstrap admin) → linked, admin retained.
6. **Session expiry & logout:** advance the idle/absolute clock (inject a short
   TTL config) → next request 401; `/auth/logout` → cookie cleared, subsequent
   request with the old cookie 401; revocation visible on the *other* instance.
7. **Token minting:** logged-in user `POST /auth/tokens` → gets a plaintext token
   once → use that token as `X-NuGet-ApiKey` against a slice-1 NuGet repo endpoint
   and succeed (end-to-end proof the minted token is a real slice-1 token).
8. **JWKS rotation:** mock rotates its signing key + `kid`; an ID token signed
   with the new key validates (kid-miss refetch), and a token signed with a
   retired key after rotation fails.
9. **(Optional, gated on Redis container)** revoke a session on A → B's L1 drops
   it via the invalidation backplane → B rejects immediately.

## 6. Security & failure modes

- **Open redirect:** `redirect_to` is validated to be a **relative path** (must
  start with a single `/`, not `//`, no scheme/host); anything else → `/`. Same
  rule for any post-logout redirect that isn't the configured IdP
  `end_session_endpoint`.
- **CSRF on the callback:** the `state` parameter (random, single-use, stored in
  `oidc_flow`) is the CSRF token for the login flow; `nonce` binds the ID token to
  this flow; **PKCE** binds the code to this client. All three must match or the
  callback is rejected. Because we deliberately don't use a pre-flight cookie, a
  forged callback with an attacker's `code`/`state` fails the `oidc_flow` lookup.
- **State/nonce/PKCE storage:** in **Postgres** (`oidc_flow`), short-lived,
  single-use (atomic `DELETE … RETURNING`), reaped on expiry — never in memory,
  satisfying the scale-out constraint and preventing cross-instance flow loss.
- **Token leakage:** ID/access tokens from the IdP are used transiently during
  the callback and **never persisted** (no refresh-token storage). Session cookie
  is `HttpOnly` (no JS access) + `Secure`. The DB stores only the **sha256** of
  the session cookie value and of slice-1 tokens; a DB read doesn't yield usable
  credentials. `client_secret` is redacted from APIs (encryption at rest =
  §12.5).
- **Clock skew:** `exp`/`nbf`/`iat` validated with a configurable leeway
  (default 60s) to tolerate small clock drift between forge and Entra.
- **JWKS rotation / key confusion:** keys looked up by `kid`; kid-miss forces a
  singleflight refetch; reject tokens whose `alg` isn't an expected asymmetric
  alg (no `alg: none`, no HMAC-with-public-key confusion — `openidconnect`
  enforces this, but assert it). Cache invalidation broadcast on refetch keeps
  peers consistent.
- **Replay:** `state` single-use blocks code/state replay; `nonce` single-use
  (tied to the consumed flow row) blocks ID-token replay; PKCE blocks
  authorization-code interception/replay by another client.
- **Session fixation:** session id is server-generated only at successful login;
  rotated on privilege change; no client-supplied session id is ever honored.
- **SSRF on IdP endpoints:** discovery/JWKS/token URLs come from config + the
  IdP's own discovery doc. Apply the slice-1 SSRF posture (scheme allowlist,
  timeouts, bounded redirects) to the OIDC HTTP client; the `issuer` is
  operator-configured (trusted), but the discovery-advertised `jwks_uri`/token
  endpoint should still be sanity-checked against the issuer host.
- **Username-claim hijack:** linking an OIDC identity to an existing local user by
  username is risky if the username claim is attacker-influenced. Default to a
  verified, stable claim; document `link_existing_by_username = false` for
  hardened deployments; never link on email alone.
- **Account-state checks:** reject login if the resolved/linked `app_user.active =
  false` even when the IdP authenticates successfully.

## 7. Open questions / risks

1. **Slice-1 middleware seam shape.** This plan assumes the slice-1
   principal-extraction middleware can accept an additional "session cookie"
   principal source and exposes a `User` type constructible from a session row.
   If slice 1 hard-codes only token/basic, a small refactor is needed first.
   **Flagged assumption.**
2. **Overlap with §12.3 (credential-forwarding provider chain).** Both this slice
   and §12.3 introduce an "authentication provider." Decision here: ship OIDC as a
   concrete login path and shape its entry as a single `AuthenticationProvider`-ish
   method, but **do not** build the ordered provider-chain abstraction — that's
   §12.3's deliverable, which will generalize local-password + upstream-basic +
   this OIDC path into a chain. Risk: if §12.3 lands first or concurrently, align
   on the trait signature to avoid rework. Recommend sequencing §12.2 before
   §12.3 and letting §12.3 absorb the seam.
3. **Entra "groups overage."** Large group memberships make Entra emit a
   `_claim_names`/`_claim_sources` Graph pointer instead of inline `groups`. This
   slice recommends **app roles** (`roles` claim) to sidestep it; supporting the
   Graph callout for raw-group admin mapping is deferred.
4. **Refresh tokens / IdP-session coupling.** We intentionally don't store refresh
   tokens; forge sessions are independent and users re-login on expiry. If silent
   renewal is later desired, revisit (adds refresh-token storage → encryption-at-
   rest §12.5 interplay).
5. **Single OIDC provider.** Schema is multi-provider ready (`issuer` column) but
   the slice wires one. Multi-IdP selection UI/routing is a later concern.
6. **Mid-session admin revocation.** `is_admin` is recomputed at login, not live;
   a user de-admined in Entra keeps admin until their session expires/re-logs.
   Live re-evaluation belongs to the RBAC slice (§12.4).
7. **`SameSite=Lax` vs `Strict`.** Lax is required for the IdP redirect to carry
   the session cookie on the final navigation; we rely on state/nonce/PKCE + CSRF
   double-submit for the rest. If a stricter posture is mandated, a
   `SameSite=Strict` + separate landing-redirect dance would be needed.
